SQL Query Fundamentals

SQL Logical Query Execution Order

SQL queries are logically processed in a specific sequence distinct from their written order:

1. FROM & JOIN (Identify tables & merge) → 2. ON (Join conditions) → 3. WHERE (Filter raw rows) → 4. GROUP BY (Aggregate rows) → 5. HAVING (Filter groups) → 6. SELECT (Choose columns) → 7. DISTINCT (Remove duplicates) → 8. ORDER BY (Sort result) → 9. LIMIT / OFFSET (Paginate)

WHERE vs HAVING

This distinction appears frequently in interviews.

  • WHERE filters individual rows before grouping.
  • HAVING filters groups after aggregation.

Learn to convert problem statements into SQL

When you read a SQL problem, don't start typing immediately. First, translate the question into a plan.

Use this six-step framework for almost every problem.

  1. Identify the output. What columns must the result contain? One row per employee, department, customer, or something else?
  2. Identify the source tables. Which table contains the information? Do you need to join multiple tables?
  3. Identify the row-level conditions. Does the question specify a date, salary threshold, status, or category? Think WHERE.
  4. Check whether aggregation is needed. Are you calculating counts, totals, averages, or one result per group? Think GROUP BY.
  5. Identify ranking or comparison requirements. Does it ask for the highest, second-highest, top three, latest, or previous row? Consider sorting, subqueries, or window functions.
  6. Check edge cases. What happens with ties, NULL values, duplicate rows, empty matches, or multiple records per person?

Types of SQL joins

1. INNER JOIN

Returns only rows that have matching records in both tables.

SQL
SELECT e.name, d.dept_name
FROM Employees e
INNER JOIN Departments d
    ON e.dept_id = d.dept_id;

Use when only matched records are required.

2. LEFT JOIN

Returns every row from the left table and matching rows from the right table. Unmatched right-side columns become NULL.

SQL
SELECT e.name, d.dept_name
FROM Employees e
LEFT JOIN Departments d
    ON e.dept_id = d.dept_id;

Use when all employees must appear, even without a matching department.

3. RIGHT JOIN

Returns every row from the right table and matching rows from the left table.

SQL
SELECT e.name, d.dept_name
FROM Employees e
RIGHT JOIN Departments d
    ON e.dept_id = d.dept_id;

Use when every department must appear, including departments without employees.

4. FULL OUTER JOIN

Returns matched rows plus unmatched rows from both tables.

SQL
SELECT e.name, d.dept_name
FROM Employees e
FULL OUTER JOIN Departments d
    ON e.dept_id = d.dept_id;

Supported by PostgreSQL and SQL Server, but not directly by MySQL.

5. CROSS JOIN

Returns every possible combination of rows from the two tables.

SQL
SELECT e.name, d.dept_name
FROM Employees e
CROSS JOIN Departments d;

If the first table has 5 rows and the second has 3, the result has 15 rows.

Interview tip

JOIN without a qualifier generally means INNER JOIN.

SQL

Common self-join interview questions

  • Find employees earning more than their managers.
  • Find employees reporting to the same manager.
  • Find pairs of users or products meeting a relationship condition.
  • Compare records from the same table.

Multiple JOINs

Real interview problems often require three or more tables.

Consider these tables:

  • Customers(customer_id, name)
  • Orders(order_id, customer_id)
  • OrderItems(order_id, product_id, quantity)
  • Products(product_id, product_name, price)

Problem: Find the total spending of each customer

SQL
SELECT
    c.customer_id,
    c.name,
    SUM(oi.quantity * p.price) AS total_spending
FROM Customers c
JOIN Orders o
    ON c.customer_id = o.customer_id
JOIN OrderItems oi
    ON o.order_id = oi.order_id
JOIN Products p
    ON oi.product_id = p.product_id
GROUP BY
    c.customer_id,
    c.name;

How to approach multiple joins

  1. Identify the entity requested in the output: customers.
  2. Identify where the necessary information exists.
  3. Follow the relationships from customers to orders, order items, and products.
  4. Calculate the spending for each order item.
  5. Group by customer and sum the item totals.

This query returns customers who have qualifying order records. To include customers who have never ordered, use appropriate LEFT JOINs and handle NULL totals with COALESCE().

JOIN condition: ON vs. WHERE

This is a common interview trap, particularly with outer joins.

Suppose we want all employees, but we only want department information when the department is IT.

Correct for this requirement:

SQL
SELECT e.name, d.dept_name
FROM Employees e
LEFT JOIN Departments d
    ON e.dept_id = d.dept_id
   AND d.dept_name = 'IT';

All employees remain in the result. Employees who aren't matched to IT have NULL department information.

Different behavior:

SQL
SELECT e.name, d.dept_name
FROM Employees e
LEFT JOIN Departments d
    ON e.dept_id = d.dept_id
WHERE d.dept_name = 'IT';

The WHERE clause removes rows where the department name is NULL, so employees without a matching IT department are removed. The query effectively behaves like an inner join for this condition.

Remember
  • ON determines which rows match.
  • WHERE filters the result after the join's matching and outer-row preservation.

JOIN vs. subquery vs. EXISTS

There are multiple ways to solve the same problem.

Problem: Find customers who have placed at least one order

Using JOIN:

SQL
SELECT DISTINCT c.customer_id, c.name
FROM Customers c
JOIN Orders o
    ON c.customer_id = o.customer_id;

DISTINCT avoids repeated customers when they have multiple orders.

Using EXISTS:

SQL
SELECT c.customer_id, c.name
FROM Customers c
WHERE EXISTS (
    SELECT 1
    FROM Orders o
    WHERE o.customer_id = c.customer_id
);

EXISTS checks whether at least one matching order exists without multiplying the customer row in the output.

For questions that ask whether a matching record exists, EXISTS is often a clean choice. For questions that require columns from both tables, a join is usually more natural.

Important JOIN edge cases

Duplicate matches can multiply rows

Suppose one customer has three orders. Joining the customer with orders returns three rows for that customer.

This is expected behavior, not a bug.

Before writing an aggregate query, ask: What does one row represent after the join?

If you sum values after joining tables with one-to-many or many-to-many relationships, you may accidentally double-count data.

NULL values don't match with =

SQL
ON A.key = B.key

Two NULL values do not satisfy this condition in standard SQL. Use the database's NULL-safe comparison features only when the problem requires NULLs to match.

Prefer explicit JOIN syntax

Use:

SQL
SELECT *
FROM A
JOIN B ON A.id = B.id;

Avoid comma-separated table lists with conditions in WHERE for ordinary join problems. Explicit joins make relationships and outer-join behavior easier to understand.

SQL Views

What is a View in SQL?

A View is a virtual table created using the result of a SQL query. It does not normally store the actual result data; instead, it stores the query definition and retrieves data from the underlying tables when accessed.

A view can contain selected columns, filtered rows, joins, aggregate functions, and other SQL operations.

Syntax

SQL
CREATE VIEW view_name AS
SELECT column1, column2, ...
FROM table_name
WHERE condition;

Example: Suppose we have an Employees table.

emp_idnamedepartmentsalary
1AmanIT80000
2PriyaHR60000
3RaviIT90000
4NehaFinance50000

Create a view containing only IT employees:

SQL
CREATE VIEW IT_Employees AS
SELECT emp_id, name, salary
FROM Employees
WHERE department = 'IT';

Query the view just like a table:

SQL
SELECT *
FROM IT_Employees;
Output:
emp_idnamesalary
1Aman80000
3Ravi90000

The view exposes only the selected columns and rows.

Why Do We Use Views?

Views are useful for:

  1. Security: Restrict access to sensitive columns such as salaries.
  2. Simplicity: Hide complex joins and calculations behind a simple query.
  3. Reusability: Write a complex query once and reuse it.
  4. Logical data independence: Provide a stable interface even when the underlying schema changes, provided the view remains valid.
  5. Consistent reporting: Allow multiple users to use the same predefined query logic.

Example: Hide sensitive salary information

SQL
CREATE VIEW Employee_Public AS
SELECT emp_id, name, department
FROM Employees;

Users who have access only to this view can query employee details without being given direct access to the salary column.

A. Create an index

Syntax

SQL
CREATE INDEX index_name
ON table_name (column_name);

Example:

SQL
CREATE INDEX idx_employee_name
ON Employees (name);

Now queries filtering by name may benefit from the index:

SQL
SELECT *
FROM Employees
WHERE name = 'Aman';

B. Create a unique index

A unique index prevents duplicate indexed values.

SQL
CREATE UNIQUE INDEX idx_employee_email
ON Employees (email);

This is useful when every employee must have a unique email address.

Note that how NULL values are handled by unique indexes depends on the database system. A UNIQUE index is not identical to a PRIMARY KEY.

C. Create a composite index

A composite index contains multiple columns.

SQL
CREATE INDEX idx_dept_salary
ON Employees (department, salary);

This index is particularly useful for queries such as:

SQL
SELECT *
FROM Employees
WHERE department = 'IT'
  AND salary > 70000;

The column order matters. An index on (department, salary) is generally most useful when a query filters or sorts by department, or filters by department and then salary.

It may not help as effectively for a query that filters only by salary.

The syntax varies by database.

MySQL:

SQL
DROP INDEX idx_employee_name

SQL
DROP INDEX idx_employee_name;

Types of Indexes in DBMS

A. Primary Key Index

A primary key uniquely identifies each row.

SQL
CREATE TABLE Employees (
    emp_id INT PRIMARY KEY,
    name VARCHAR(100),
    salary DECIMAL(10, 2)
);

Most relational databases automatically create an index to enforce the primary key constraint.

Interview point

A primary key is a constraint; an index is a data structure. The database commonly implements the primary key using a unique index, but the concepts are different.

B. Unique Index

SQL
CREATE UNIQUE INDEX idx_email
ON Employees (email);
  • Prevents duplicate indexed values.
  • Can improve searches using email.
  • Does not necessarily prohibit multiple NULL values; this depends on the DBMS.

C. Non-Unique Index

SQL
CREATE INDEX idx_department
ON Employees (department);

Multiple employees can belong to the same department. The index helps locate rows for that department.

D. Clustered Index

A clustered index determines how table rows are organized according to the index key in database systems that support this organization.

For example, SQL Server supports clustered indexes. InnoDB in MySQL organizes table data using the primary key as its clustered index by default when a primary key exists.

SQL
-- SQL Server example
CREATE CLUSTERED INDEX idx_emp_id
ON Employees (emp_id);

Important points:

  • A table can have at most one clustered index because there can be only one physical organization of its rows.
  • The clustered index key can affect the performance of range queries.
  • Clustered-index behavior is database-specific.

E. Non-Clustered Index

A non-clustered index stores index keys and references to the corresponding table rows.

SQL
-- SQL Server example
CREATE NONCLUSTERED INDEX idx_salary
ON Employees (salary);

A table can have multiple non-clustered indexes, subject to DBMS limits.

Interview comparison

Clustered indexNon-clustered index
Determines table-row organization in supporting systemsSeparate index structure references table rows
At most one per tableMultiple can exist
Useful for suitable range and lookup queriesUseful for filtering, sorting, and lookups

Do not assume that every DBMS implements clustered and non-clustered indexes identically.

F. Composite Index

A composite index is built on two or more columns.

SQL
CREATE INDEX idx_dept_salary
ON Employees (department, salary);

This is one of the most important index concepts for SQL interviews.

Suppose the index is:

SQL
CREATE INDEX idx_abc
ON Employees (A, B, C);

The index is generally useful for these leading-column combinations:

Query conditionExpected usefulness
WHERE A = 10Good
WHERE A = 10 AND B = 20Good
WHERE A = 10 AND B = 20 AND C = 30Good
WHERE A = 10 AND C = 30Can use the leading A portion; C may be less useful for index navigation
WHERE B = 20Usually cannot efficiently seek using the leftmost prefix
WHERE C = 30Usually cannot efficiently seek using the leftmost prefix

This is called the leftmost-prefix principle. Exact optimizer behavior depends on the database and index type.

G. Composite Index: Column Order Matters

Consider these two indexes:

SQL
CREATE INDEX idx_dept_salary
ON Employees (department, salary);
CREATE INDEX idx_salary_dept
ON Employees (salary, department);

They are not equivalent.

For this query:

SQL
SELECT *
FROM Employees
WHERE department = 'IT'
  AND salary > 70000;

The index beginning with department is often a natural choice because it can narrow down the department before applying the salary range.

For this query:

SQL
SELECT *
FROM Employees
WHERE salary > 70000;

An index beginning with salary may be more suitable.

How to decide the order:

  1. Identify the actual query patterns.
  2. Consider equality filters before range filters as a useful starting heuristic.
  3. Check whether the index supports ORDER BY or GROUP BY.
  4. Verify the execution plan instead of blindly following a rule.

Column selectivity matters, but it is not the only factor determining index order.

Common Table Expression (CTE)

Overview

A Common Table Expression (CTE) is a temporary, named result set that you define using the WITH clause and use within a single SQL statement.

Why do we need CTEs?

Consider the question:

Find employees whose salary is greater than the average salary of all employees.

Suppose we have an Employee table:

idnamedepartmentsalary
1AmanIT80000
2PriyaHR50000
3RaviIT90000
4NehaHR60000
5KaranIT70000

We could solve it using a subquery:

SQL
SELECT name, salary
FROM Employee
WHERE salary > (
    SELECT AVG(salary)
    FROM Employee
);

We can also write it using a CTE:

SQL
WITH AverageSalary AS (
    SELECT AVG(salary) AS avg_salary
    FROM Employee
)
SELECT e.name, e.salary
FROM Employee e
CROSS JOIN AverageSalary a
WHERE e.salary > a.avg_salary;

Both queries solve the same problem.

The CTE gives the average calculation a meaningful name, AverageSalary, which makes the overall query easier to read and extend.

CTE syntax

SQL
WITH cte_name AS (
    SELECT column1, column2
    FROM table_name
    WHERE condition
)
SELECT *
FROM cte_name;

Understand each part:

ComponentMeaning
WITHStarts the CTE definition
cte_nameName of the temporary result set
AS (...)Contains the query defining the result set
Main queryReads from the CTE

Important points:

  • A CTE exists only for the SQL statement in which it is defined.
  • You can reference it in the main query and, where permitted, in other CTE definitions within the same WITH clause.
  • A CTE is not a permanent database table.
  • A CTE does not automatically store its result in physical memory or a temporary table. The database optimizer decides how to execute it.

Simple CTE example

Problem: Find employees earning more than ₹70,000.

SQL
WITH HighSalaryEmployees AS (
    SELECT id, name, department, salary
    FROM Employee
    WHERE salary > 70000
)
SELECT *
FROM HighSalaryEmployees;

The query works in two logical steps:

  1. HighSalaryEmployees defines the rows that satisfy the salary condition.
  2. The main query retrieves those rows.

You can think of the CTE as a named intermediate result that helps organize your query.

Multiple CTEs in one query

You can define multiple CTEs in the same WITH clause by separating their definitions with commas.

Problem: Find departments whose average salary is greater than the company's overall average salary.

SQL
WITH DepartmentAverage AS (
    SELECT
        department,
        AVG(salary) AS avg_salary
    FROM Employee
    GROUP BY department
),
CompanyAverage AS (
    SELECT AVG(salary) AS company_avg
    FROM Employee
)
SELECT
    d.department,
    d.avg_salary
FROM DepartmentAverage d
CROSS JOIN CompanyAverage c
WHERE d.avg_salary > c.company_avg;

How to approach it

  • First CTE: calculate one average per department.
  • Second CTE: calculate one average for the entire company.
  • Main query: compare each department's average with the company average.

This is a useful pattern for questions involving multiple levels of aggregation.

CTE with window functions

This is one of the most important combinations for SQL interviews.

Problem: Find the second-highest distinct salary in each department

SQL
WITH RankedEmployees AS (
    SELECT
        id,
        name,
        department,
        salary,
        DENSE_RANK() OVER (
            PARTITION BY department
            ORDER BY salary DESC
        ) AS salary_rank
    FROM Employee
)
SELECT
    name,
    department,
    salary
FROM RankedEmployees
WHERE salary_rank = 2;

SQL Window Functions

What are window functions?

A window function performs a calculation across a set of related rows while keeping each individual row in the output.

For example, suppose we have an Employee table:

namedepartmentsalary
AndrewFinance50000
BrianFinance50000
CharlesFinance20000
DanielSales30000
EthanSales20000

Suppose the question asks us to display every employee along with their department's average salary.

SQL
SELECT
    name,
    department,
    salary,
    AVG(salary) OVER (
        PARTITION BY department
    ) AS avg_salary
FROM Employee;
Output:
namedepartmentsalaryavg_salary
AndrewFinance5000040000
BrianFinance5000040000
CharlesFinance2000040000
DanielSales3000025000
EthanSales2000025000

Notice that every employee remains in the output. The average is calculated separately for each department and displayed alongside each employee.

Window functions vs. GROUP BY

This is a fundamental interview distinction.

Using GROUP BY:

SQL
SELECT department, AVG(salary) AS avg_salary
FROM Employee
GROUP BY department;

Result: one row per department.

Using a window function:

SQL
SELECT
    name,
    department,
    salary,
    AVG(salary) OVER (
        PARTITION BY department
    ) AS avg_salary
FROM Employee;

Result: one row per employee, with the department average added.

General syntax

SQL
SELECT
    column1,
    window_function(column2) OVER (
        PARTITION BY column3
        ORDER BY column4
    ) AS result
FROM table_name;

The OVER() clause defines the window used by the function.

Understand the three window configurations

A. OVER() — Entire result set

SQL
COUNT(*) OVER ()

Counts all rows in the window and displays that count on every row.

B. PARTITION BY — Separate groups

SQL
AVG(salary) OVER (
    PARTITION BY department
)

Calculates a separate average for each department without removing employee rows.

Numbers rows in descending salary order.

Rows with equal ordering values receive the same rank. Subsequent ranks skip numbers.

Interview problem: Find the second-highest salary in each department

SQL
WITH RankedEmployees AS (
    SELECT
        name,
        department,
        salary,
        DENSE_RANK() OVER (
            PARTITION BY department
            ORDER BY salary DESC
        ) AS salary_rank
    FROM Employee
)
SELECT name, department, salary
FROM RankedEmployees
WHERE salary_rank = 2;

How to approach this problem:

  1. The phrase in each department tells us to use PARTITION BY department.
  2. The phrase second-highest distinct salary tells us to use DENSE_RANK().
  3. ORDER BY salary DESC places the highest salary first.
  4. The CTE calculates the ranking.
  5. The outer query filters for rank 2.

Why use a CTE? In standard SQL, a window function's result cannot be filtered directly in the same query block's WHERE clause. The CTE lets us calculate the rank first and filter it afterward.

Window frames: running totals and moving averages

One additional concept is essential for mastering window functions: the window frame.

A window frame defines which rows within the ordered window contribute to a calculation for the current row.

Running total

Suppose we have a Sales table:

Query:

SQL
SELECT
    sale_date,
    amount,
    SUM(amount) OVER (
        ORDER BY sale_date

                 AND CURRENT ROW
    ) AS running_total
FROM Sales;

The frame begins at the first row and extends through the current row.

Moving average

SQL
SELECT

    amount,
    AVG(amount) OVER (
        ORDER BY sale_date
        ROWS BETWEEN 1 PRECEDING

FROM Sales;

LAG() retrieves a value from a previous row in the ordered window without performing a self join.

LAG()

Looks backward in the specified order.

Example: Today's sales versus yesterday's sales.

LEAD()

Looks forward in the specified order.

Example: Today's order versus the customer's next order.

FIRST_VALUE() — Get the first value in a window

Returns the value from the first row of the window frame.

SQL
SELECT
    name,
    department,
    salary,
    FIRST_VALUE(salary) OVER (
        PARTITION BY department
        ORDER BY salary DESC
    ) AS highest_salary
FROM Employee;

This displays the highest salary alongside every employee in each department, assuming the window starts with the highest-paid employee.

Use cases:

  • Find the first transaction in a group.
  • Display the earliest order date.
  • Compare every employee's salary against the highest salary in their department.

LAST_VALUE() — Get the last value in a window

Returns the value from the last row of the window frame.

One important trap: the default window frame with ORDER BY often ends at the current row's peer group, rather than the end of the entire partition. As a result, LAST_VALUE() may return the current row's value instead of the final value in the partition.

Correct way to get the lowest salary in each department

SQL
SELECT
    name,
    department,
    salary,
    LAST_VALUE(salary) OVER (
        PARTITION BY department
        ORDER BY salary ASC
        ROWS BETWEEN UNBOUNDED PRECEDING
                 AND UNBOUNDED FOLLOWING
    ) AS lowest_salary
FROM Employee;

Here, the frame explicitly extends to the last row of the partition.

Interview tip

Whenever you need the last value in the entire partition, check the window frame carefully.

NTH_VALUE() — Get the Nth value

Returns the value from the Nth row of the window frame, if that row exists.

SQL
SELECT
    name,
    salary,
    NTH_VALUE(salary, 2) OVER (
        ORDER BY salary DESC
        ROWS BETWEEN UNBOUNDED PRECEDING
                 AND UNBOUNDED FOLLOWING
    ) AS second_salary
FROM Employee;

This retrieves the second salary in the ordered window frame. Because ties may exist, this does not necessarily mean the second-highest distinct salary.

Use cases:

  • Retrieve a value at a specific position.
  • Compare a record with the second or third ordered record.
  • Analyze ordered measurements.

For a second-highest distinct salary problem, DENSE_RANK() is usually a better choice.

NTILE(N) — Divide rows into buckets

Divides the ordered rows into up to N approximately equal-sized buckets, numbered from 1 through N.

SQL
SELECT
    name,
    salary,
    NTILE(4) OVER (
        ORDER BY salary DESC
    ) AS salary_quartile
FROM Employee;

This distributes the employees into four groups based on salary order.

Use cases:

  • Divide customers into four groups.
  • Create salary bands based on ordered rows.
  • Split users into approximately equal-sized cohorts.

Note that NTILE() divides rows, not distinct salary values, so tied salaries can end up in different buckets.

Top 20 SQL CTE Patterns

Overview

A Common Table Expression (CTE) is a temporary named result set defined using WITH. It helps divide a complex SQL query into readable steps.

SQL
WITH CTE_Name AS (
    SELECT ...
)
SELECT *
FROM CTE_Name;

Pattern 1. Basic Readability — Replace Nested Subqueries

Use when

You want to name an intermediate result and simplify a complex query.

SQL
WITH HighSales AS (
    SELECT order_id, customer_id, amount
    FROM Orders
    WHERE amount > 1000
)
SELECT c.name, h.amount
FROM Customers c
JOIN HighSales h
    ON c.customer_id = h.customer_id;

How it works:

  1. HighSales selects orders above 1000.
  2. The main query joins those orders with customers.
  3. The CTE makes the logic easier to read and reuse within the statement.

Pattern 2. Multiple CTEs — Chain Logic Steps

Use when

A problem requires multiple intermediate calculations.

SQL
WITH Sales2023 AS (
    SELECT product_id, amount
    FROM Sales
    WHERE sale_date >= DATE '2023-01-01'
      AND sale_date < DATE '2024-01-01'
),
Sales2024 AS (
    SELECT product_id, amount
    FROM Sales
    WHERE sale_date >= DATE '2024-01-01'
      AND sale_date < DATE '2025-01-01'
)
SELECT a.product_id,
       a.amount AS sales_2023,
       b.amount AS sales_2024
FROM Sales2023 a
JOIN Sales2024 b
    ON a.product_id = b.product_id;
Remember

Separate CTEs with commas. Later CTEs can reference earlier CTEs. This example joins individual sales rows; if you need yearly product totals, aggregate each CTE by product_id first.

Pattern 3. Recursion — Generate Numbers from 1 to 10

Use when

You need a sequence, hierarchy traversal, or repeated processing of rows.

SQL
WITH RECURSIVE NumSeries AS (
    SELECT 1 AS n              -- Anchor
    UNION ALL
    SELECT n + 1               -- Recursive step
    FROM NumSeries
    WHERE n < 10               -- Stop condition
)
SELECT n
FROM NumSeries;

Output: 1, 2, 3, ..., 10

The recursive CTE has three parts:

  • Anchor: Starts with 1.
  • Recursive step: Generates the next number.
  • Termination: Stops generating numbers after 10.

PostgreSQL supports WITH RECURSIVE. SQL Server uses WITH for recursive CTEs and generally does not use the RECURSIVE keyword.

Pattern 4. Manager Hierarchy — Who Reports to Whom?

Use when

An employee table contains a manager_id that references another employee.

Example structure:

    SELECT id, name, manager_id, 1 AS lvl
    FROM Employees

Start at the root of the organization and repeatedly find employees whose manager_id matches the current employee's id.

Pattern 6. Delete Duplicates — ROW_NUMBER()

Use when

You need to retain one row per email and remove the rest.

PostgreSQL example:

SQL
WITH RankedUsers AS (
    SELECT id,
           ROW_NUMBER() OVER (
               PARTITION BY email
               ORDER BY id
           ) AS rn
    FROM Users
)
DELETE FROM Users u
USING RankedUsers r
WHERE u.id = r.id
  AND r.rn > 1;

How it works:

  1. PARTITION BY email groups rows with the same email.
  2. ORDER BY id selects the row with the smallest ID as rn = 1.
  3. Rows with rn > 1 are duplicates.
  4. The DELETE removes only those duplicate rows.

The original image's DELETE FROM DupeRows pattern is not universally valid. In PostgreSQL, use DELETE ... USING; SQL Server supports deleting through an updatable CTE.

Before deleting: Run the ranking query as a SELECT first to verify which rows will be removed. Decide explicitly how NULL emails and case differences should be treated.

Pattern 10. Date Generation — Fill Missing Dates

Use when

A report must include every date even when no sales occurred.

PostgreSQL recursive CTE example:

SQL
WITH RECURSIVE Calendar AS (
    SELECT DATE '2024-01-01' AS dt

    UNION ALL

    SELECT dt + 1
    FROM Calendar
    WHERE dt < DATE '2024-01-31'
),
DailySales AS (
    SELECT sale_date,
           SUM(amount) AS amount
    FROM Sales

FROM Calendar c

    ON c.dt = s.sale_date

Pattern 11. Year-over-Year Growth — LAG() + CTE

Use when

You need to compare annual revenue, profit, or sales with the previous year.

Pattern 12. Monthly Active Users — Retention Analysis

Use when

You need to count active users per month and determine how many return the following month.

Assume Logins(user_id, login_date).

SQL
WITH MonthlyUsers AS (
    SELECT DISTINCT
           user_id,
           DATE_TRUNC('month', login_date)::date AS month
    FROM Logins
)
SELECT m1.month,
       COUNT(*) AS active_users,
       COUNT(m2.user_id) AS retained_next_month
FROM MonthlyUsers m1
LEFT JOIN MonthlyUsers m2
    ON m1.user_id = m2.user_id
   AND m2.month = (m1.month + INTERVAL '1 month')::date
GROUP BY m1.month
ORDER BY m1.month;

How it works:

  1. DISTINCT ensures each user appears at most once per month.
  2. m1 represents users active in a particular month.
  3. m2 finds the same users in the next month.
  4. COUNT(*) counts current-month active users.
  5. COUNT(m2.user_id) counts users retained into the next month.

Retention rate can be calculated as:

SQL
ROUND(
    100.0 * COUNT(m2.user_id) / NULLIF(COUNT(*), 0),
    2
) AS retention_pct

Add this expression to the SELECT list above.

Pattern 15. Basket Analysis — Products Bought Together

Use when

You need to find which product pairs most frequently appear in the same order.

Assume Order_Items(order_id, product_id).

SQL
WITH Pairs AS (
    SELECT a.product_id AS p1,
           b.product_id AS p2,
           a.order_id
    FROM Order_Items a
    JOIN Order_Items b
        ON a.order_id = b.order_id
       AND a.product_id < b.product_id
)
SELECT p1,
       p2,
       COUNT(DISTINCT order_id) AS frequency
FROM Pairs
GROUP BY p1, p2
ORDER BY frequency DESC;

Why a.product_id < b.product_id?

For a pair of products A and B, it avoids generating both (A, B) and (B, A), and prevents pairing a product with itself.

COUNT(DISTINCT order_id) avoids overcounting if the source contains repeated lines for the same product in one order.

Pattern 16. Pivot Preparation — Rows to Columns

Use when

You want quarterly sales displayed in separate columns.

Assume Sales(year, quarter, revenue).

SQL
WITH BaseData AS (
    SELECT year,
           quarter,
           SUM(revenue) AS revenue
    FROM Sales
    GROUP BY year, quarter
)
SELECT year,
       MAX(CASE WHEN quarter = 1 THEN revenue END) AS Q1,
       MAX(CASE WHEN quarter = 2 THEN revenue END) AS Q2,
       MAX(CASE WHEN quarter = 3 THEN revenue END) AS Q3,
       MAX(CASE WHEN quarter = 4 THEN revenue END) AS Q4
FROM BaseData
GROUP BY year
ORDER BY year;

Intuition

CASE selects the revenue for a particular quarter. MAX() combines those selected values into one row per year.

This is called conditional aggregation. MAX() is appropriate here because the CTE already contains at most one row per year and quarter.

Pattern 17. Consecutive Wins — Find Three Wins in a Row

Use when

You need to identify players or teams with consecutive wins.

Assume Matches(id, player_id, match_date, result).

SQL
WITH Streaks AS (
    SELECT id,
           player_id,
           match_date,
           result,
           LAG(result, 1) OVER (
               PARTITION BY player_id
               ORDER BY match_date, id
           ) AS prev1,
           LAG(result, 2) OVER (
               PARTITION BY player_id
               ORDER BY match_date, id
           ) AS prev2
    FROM Matches
)
SELECT *
FROM Streaks
WHERE result = 'Win'
  AND prev1 = 'Win'
  AND prev2 = 'Win';

How it works:

  • prev1 gives the previous match result.
  • prev2 gives the result two matches earlier.
  • If all three results are Win, the current match completes a three-win streak.

PARTITION BY player_id prevents one player's result from being compared with another player's result.

If matches have gaps in dates, this still means three consecutive matches, not necessarily three consecutive calendar days.

Pattern 18. Update via CTE — Modify Data Safely

Use when

You want to identify rows with a CTE and update the underlying table.

PostgreSQL example:

SQL
WITH ToUpdate AS (
    SELECT id
    FROM Employees
    WHERE performance_score > 90
)
UPDATE Employees e
SET salary = e.salary * 1.10
FROM ToUpdate t
WHERE e.id = t.id;

This increases salaries by 10% for employees with a performance score above 90.

Important

A CTE is not automatically an independent temporary table. The UPDATE changes the underlying Employees table.

In SQL Server, an updatable CTE can also be used directly:

SQL
WITH ToUpdate AS (
    SELECT *
    FROM Employees
    WHERE performance_score > 90
)
UPDATE ToUpdate
SET salary = salary * 1.10;

Syntax and updateability depend on the database. For important data changes, inspect the target rows first and use a transaction where appropriate.

Pattern 19. Tree Path Generation — Build Breadcrumbs

Use when

You need full category paths such as Home > Electronics > TV.

Assume Categories(id, name, parent_id).

PostgreSQL example:

SQL
WITH RECURSIVE Paths AS (
    SELECT id,
           name,
           parent_id,
           name::text AS path
    FROM Categories
    WHERE parent_id IS NULL

    UNION ALL

    SELECT c.id,
           c.name,
           c.parent_id,
           p.path || ' > ' || c.name
    FROM Categories c
    JOIN Paths p
        ON c.parent_id = p.id
)
SELECT id, name, path
FROM Paths
ORDER BY id;

Example path:

Output

Intuition
  1. The anchor selects root categories.
  2. The recursive step finds each category's children.
  3. The path is extended by appending the child's name.

The hierarchy should not contain cycles; otherwise, recursion may continue indefinitely unless you add cycle detection or a depth limit.

Pattern 20. Insert from CTE — ETL and Data Migration

Use when

You need to calculate or transform data before inserting aggregated results into another table.

Assume Raw_Sales(region, amount) and Summary_Table(region, total_sales).

SQL
WITH CalculatedData AS (
    SELECT region,
           SUM(amount) AS total_sales
    FROM Raw_Sales
    GROUP BY region
)
INSERT INTO Summary_Table (region, total_sales)
SELECT region, total_sales
FROM CalculatedData;

How it works:

  1. CalculatedData aggregates sales by region.
  2. INSERT INTO stores the calculated results in the summary table.

The destination table must exist and have compatible columns. Re-running this query may insert duplicate summary rows unless you truncate the table, enforce suitable uniqueness, or use an appropriate upsert strategy.

The position of WITH relative to INSERT varies by SQL dialect; the example uses PostgreSQL-compatible syntax.

6. Understand INNER JOIN vs. EXISTS

Using EXISTS to find customers who have placed at least one order:

SQL
SELECT c.name
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.id
);

Equivalent using INNER JOIN:

SQL
SELECT DISTINCT c.name
FROM customers c
INNER JOIN orders o
    ON o.customer_id = c.id;

9. Compare today's active users with yesterday's active users

Assume activity_date is a DATE column and active users are identified by distinct user_id values.

SQL
WITH daily_users AS (
    SELECT
        activity_date,
        COUNT(DISTINCT user_id) AS user_count
    FROM activity_log
    WHERE activity_date IN (
        CURRENT_DATE,
        CURRENT_DATE - 1
    )
    GROUP BY activity_date
)
SELECT
    MAX(CASE
        WHEN activity_date = CURRENT_DATE
        THEN user_count
    END) AS today_users,
    MAX(CASE
        WHEN activity_date = CURRENT_DATE - 1
        THEN user_count
    END) AS yesterday_users
FROM daily_users;

Logic:

  1. The CTE calculates distinct active users for each date.
  2. CASE places today's and yesterday's counts into separate columns.
  3. MAX() combines those values into one result row.
Concept

CTE and conditional aggregation.

Note

If a date has no activity, its count appears as NULL. Use COALESCE(..., 0) if you want zero instead.

10. Use a recursive CTE to retrieve an employee hierarchy

Assume employees.id identifies an employee and parent_id identifies their manager.

SQL
WITH RECURSIVE org_chart AS (
    -- Base case: top-level employees
    SELECT
        id,
        parent_id,
        1 AS level
    FROM employees
    WHERE parent_id IS NULL

    UNION ALL

    -- Recursive case: find each employee's reports
    SELECT
        e.id,
        e.parent_id,
        oc.level + 1
    FROM employees e
    JOIN org_chart oc
        ON e.parent_id = oc.id
)
SELECT *
FROM org_chart
ORDER BY level, id;

Logic:

  1. The anchor query finds top-level employees.
  2. The recursive query finds employees reporting to the previous level.
  3. level + 1 records the hierarchy depth.
  4. Recursion continues until no additional matching employees are found.
Concept

Recursive CTEs for hierarchical data.

Important

This example assumes a valid hierarchy. Cyclic reporting relationships require cycle prevention.

13. Find the first and last transaction for each user

SQL
SELECT *
FROM (
    SELECT
        t.*,
        ROW_NUMBER() OVER (
            PARTITION BY user_id
            ORDER BY tx_date ASC, transaction_id ASC
        ) AS rn_asc,
        ROW_NUMBER() OVER (
            PARTITION BY user_id
            ORDER BY tx_date DESC, transaction_id DESC
        ) AS rn_desc
    FROM transactions t
) ranked
WHERE rn_asc = 1
   OR rn_desc = 1;

Logic:

  1. rn_asc = 1 identifies the first transaction for each user.
  2. rn_desc = 1 identifies the last transaction.
  3. The outer query returns rows matching either condition.
Concept

ROW_NUMBER() and window functions.

Important

This assumes transaction_id is a unique tie-breaker. A user with only one transaction has the same row qualify as both first and last, so it appears only once.

14. Detect gaps between sequential dates

SQL
SELECT
    event_date,
    LAG(event_date) OVER (
        ORDER BY event_date
    ) AS prev_date,
    event_date - LAG(event_date) OVER (
        ORDER BY event_date
    ) AS gap
FROM events
ORDER BY event_date;

Logic:

  1. LAG() retrieves the previous row's date.
  2. Subtract the previous date from the current date.
  3. A gap greater than one day indicates missing calendar days, assuming one row per date and date values are consecutive at daily granularity.
Concept

LAG() and date arithmetic.

Note

This subtraction syntax works in PostgreSQL for DATE values. In other databases, use the appropriate date-difference function. If duplicate dates exist, deduplicate them first to detect calendar gaps correctly.

15. Calculate cumulative spend per customer per month

SQL
SELECT
    customer_id,
    month,
    spend,
    SUM(spend) OVER (
        PARTITION BY customer_id
        ORDER BY month
        ROWS BETWEEN UNBOUNDED PRECEDING
                 AND CURRENT ROW
    ) AS cumulative_spend
FROM monthly_spend
ORDER BY customer_id, month;

Logic:

  1. PARTITION BY customer_id starts a separate running total for each customer.
  2. ORDER BY month processes each customer's records chronologically.
  3. SUM() accumulates spend from the first row through the current row.
Concept

Running totals using window functions.

Important

This assumes one row per customer per month. If multiple rows can share the same month, aggregate them first or define a unique ordering.

10. Find the Top 3 Dishes for Each Restaurant in New York

SQL
WITH DishSales AS (
    SELECT
        RestaurantID,
        City,
        DishName,
        SUM(Quantity) AS TotalQuantity
    FROM Orders
    WHERE City = 'New York'
    GROUP BY RestaurantID, City, DishName
),
RankedDishes AS (
    SELECT
        RestaurantID,
        City,
        DishName,
        TotalQuantity,
        ROW_NUMBER() OVER (
            PARTITION BY RestaurantID, City
            ORDER BY TotalQuantity DESC, DishName
        ) AS rn
    FROM DishSales
)
SELECT
    RestaurantID,
    City,
    DishName,
    TotalQuantity
FROM RankedDishes
WHERE rn <= 3
ORDER BY RestaurantID, rn;
Intuition
  1. DishSales calculates total quantity per dish and restaurant.
  2. ROW_NUMBER() ranks dishes separately for each restaurant.
  3. rn <= 3 keeps the top three dishes per restaurant.

I used ROW_NUMBER() to return at most three dishes per restaurant. The secondary ordering by DishName makes ties deterministic.

If the requirement is to include every dish tied within the top three ranks, use RANK() or DENSE_RANK() instead.
