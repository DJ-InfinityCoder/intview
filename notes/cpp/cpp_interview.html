C++ Fundamentals & Core Language

What is C++?

C++ is a general-purpose, compiled programming language that supports multiple programming paradigms, including procedural, object-oriented, and generic programming.

One important strength of C++ is that it gives you control over memory and performance while still providing high-level abstractions.

Procedural Programming

Procedural programming is a paradigm based on the concept of procedure calls, where a program is treated as a linear, step-by-step sequence of instructions. It focuses strictly on the actions and functions required to complete a task. Data and the functions that manipulate that data are kept completely separate.

Key Traits: Top-down approach, heavy reliance on global/local variables, and standalone functions.

Real-world Analogy: A cooking recipe. You follow a list of step-by-step instructions (functions) to manipulate raw ingredients (data) until the meal is complete.

Object-Oriented Programming (OOP)

Object-Oriented Programming is a paradigm centered around objects rather than actions. It focuses on the data entities you want to manipulate. Instead of separating data from logic, OOP binds data and its associated behaviors together into cohesive units called classes.

Key Traits: Bottom-up approach, centered on the four pillars: Encapsulation (hiding data), Inheritance (reusing code), Polymorphism (dynamic behavior), and Abstraction (simplifying interfaces).

Real-world Analogy: A smart car. The car contains its internal state (fuel level, speed) and its behaviors (accelerate, brake) all wrapped inside one physical asset. You interact with it through a simple dashboard interface without needing to know how the engine works internally.

How C++ acts as a Procedural Language:

If you want, you can write a massive, complex C++ program without creating a single class. You can declare global variables, write standalone functions, use structs to hold plain data, and use pointers to manipulate memory directly just like traditional C code.

How C++ acts as an Object-Oriented Language:

When your project grows large and difficult to manage structurally, you can shift completely to OOP. C++ gives you the class keyword, private/public access specifiers to lock down data security, inheritance hierarchies to extend code, and virtual functions to achieve runtime polymorphism.

By functioning as a hybrid language, C++ lets developers write high-level object-oriented architectures for application design while dropping down into procedural, low-level optimization routines exactly where performance matters most.

C++ supports multiple programming paradigms:

Procedural       → functions, loops, conditions
Object-oriented → classes, inheritance, polymorphism
Generic          → templates
Functional style → lambdas, algorithms

Why is C++ called a middle-level language?

C++ is sometimes informally called a middle-level language because it provides both high-level abstractions such as classes and templates and low-level features such as pointers, manual memory management, and direct memory manipulation.

What is the difference between C and C++?

C is primarily a procedural programming language, while C++ supports procedural, object-oriented, and generic programming. C++ provides features such as classes, inheritance, polymorphism, function/operator overloading, templates, exceptions, and the STL that are not part of C.

What are namespaces in C++?

A namespace is a named scope used to organize identifiers and prevent naming conflicts. The C++ standard library is inside the std namespace.

Its primary purpose is name organization and avoiding naming conflicts.

Simple explanation

Suppose two libraries both have a function called print().

Without namespaces:

C++ 
print();

Which print() should be called?

Namespaces allow us to separate them:

C++ 
namespace A {
    void print() {
        cout << "A";
    }
}

namespace B {
    void print() {
        cout << "B";
    }
}

Now:

C++ 
A::print();
B::print();

The :: operator is called the scope resolution operator.

Code example

C++ 
#include <iostream>

namespace First {
    int value = 10;
}

namespace Second {
    int value = 20;
}

int main() {
    std::cout << First::value << '\n';
    std::cout << Second::value << '\n';

    return 0;
}
Output:
Output 
10
20

Class vs. Struct

  • Default Access: In a class, all members are private by default. In a struct, all members are public by default.
  • Inheritance Access: Inheritance defaults to private for classes and public for structs.
  • Convention: Developers use struct for plain data records and class when writing complex systems with private states and member functions.

Struct vs. Union

An union is a special user-defined data type in C++ where all members share the exact same memory location.

Unlike a struct or a class, which allocates separate memory space for every single member, a union allocates only enough memory to hold its largest member. This means a union can store the value of only one member at a time. Writing data to a new member automatically overwrites the data of the previous one.

Imagine you have a variable that needs to hold either an int (4 bytes) OR a double (8 bytes), but never both at the same time.

  • A struct creates separate slots: It takes 12 bytes (4 + 8) plus alignment padding.
  • A union overlays the slots: It takes only 8 bytes (the size of the double). The integer just sits at the beginning of those same 8 bytes.

Enums

An enum (short for enumeration) is a user-defined data type in C++ used to assign human-readable names to integral constants.

Instead of using vague, unreadable numbers (like 0, 1, 2) to represent states in your code, an enum allows you to use meaningful words (like Low, Medium, High), making your code self-documenting and much easier to maintain.

Introduced in C++11, enum class is the modern standard used in production environments because it fixes the security flaws of traditional enums.

C++ 
#include <iostream>

enum class Status {
    Pending = 10, // You can explicitly assign start values
    Approved,     // Automatically becomes 11
    Rejected      // Automatically becomes 12
};

int main() {
    // 1. Scoped Scope: You MUST use the 'Status::' prefix
    Status current = Status::Pending;

    // 2. Strong Type Safety: This line will cause a COMPILER ERROR:
    // if (current == 10) { }

    // To compare against an integer, you must explicitly typecast it:
    if (static_cast<int>(current) == 10) {
        std::cout << "Status is pending!\n";
    }

    std::cout << "Size of enum: " << sizeof(current) << " bytes\n"; // Defaults to 4 bytes (int)
    return 0;
}

What is a class and what is an object?

A class is a user-defined type that defines data and behavior, while an object is an instance of that class. The class defines the structure, and the object represents an actual instance with its own state.

Simple explanation

Think of:

Class  → Blueprint
Object → Actual instance

class Car {
public:
    string brand;

    void drive() {
        cout << "Car is driving\n";
    }
};

Create objects:

C++ 
Car car1;
Car car2;

Both objects belong to the same class but can have different state:

C++ 
car1.brand = "BMW";
car2.brand = "Audi";

Does a class occupy memory?

The class definition itself does not represent an object instance with per-object storage.

When objects are created, memory is allocated for their non-static data members, along with any implementation-specific overhead such as a vptr for a polymorphic object.

Static data members have separate storage and are not duplicated for each object.

Common trap / wrong answer

Don't simply say:

Class takes zero memory.

That's too absolute because class-related entities can have storage, such as static data members, and objects can have implementation-specific overhead.

What are access specifiers in C++?

C++ provides three main access specifiers: public, private, and protected. They control which parts of a class can access its members.

public

Accessible from anywhere where the object is accessible.

C++ 
class A {
public:
    int x;
};

private

Accessible only from within the class and its friends.

C++ 
class A {
private:
    int x;
};

protected

Accessible from:

  • The class itself
  • Friend declarations
  • Derived classes
C++ 
class A {
protected:
    int x;
};

What is encapsulation in C++?

Encapsulation is the process of combining data members and member functions into a single unit (class) while restricting direct access to the data.

Usually, we make data members private and provide public methods to access or modify them.

Example

C++ 
class BankAccount {
private:
    double balance = 0;

public:
    void deposit(double amount) {
        if (amount > 0) {
            balance += amount;
        }
    }

    double getBalance() const {
        return balance;
    }
};

Outside code cannot directly do:

C++ 
account.balance = -1000;

because balance is private.

Instead, it must use:

C++ 
account.deposit(1000);

Why is encapsulation useful?

It provides:

  • Data protection
  • Controlled modification
  • Better maintainability
  • Clear interfaces
  • Reduced coupling
Common trap / wrong answer

Don't say:

Encapsulation means only making variables private.

Private members are one mechanism used to achieve encapsulation. Encapsulation is the broader design concept.

What is abstraction in C++?

Abstraction means exposing only the necessary functionality while hiding unnecessary implementation details from the user.

Abstraction means: Show what an object can do, but hide how it does it.

Real-world example:

When using an ATM, you know:

C++ 
withdraw();
deposit();
checkBalance();

But you don't need to know how the bank internally processes the transaction.

Simple example

Consider:

C++ 
class Car {
public:
    void start() {
        // Complex internal operations
        // fuel system
        // ignition
        // engine control
        // etc.
    }
};

The user only needs:

C++ 
car.start();

They don't need to know every internal step involved in starting the engine.

That's abstraction.

Abstract class

Pure virtual function

Abstract Classes:

An abstract class is a class that contains at least one pure virtual function. It serves as a base class that defines a common interface while leaving the implementation of specific operations to derived classes.

  • An abstract class contains at least one pure virtual function.
  • Objects of an abstract class cannot be instantiated.
  • Derived classes must implement the pure virtual functions.
  • It provides a common interface to achieve abstraction.

In C++, abstraction can be achieved using abstract classes and pure virtual functions.

C++ 
#include <iostream>

// 1. ABSTRACT CLASS
class Animal {
public:
    // Pure virtual function makes this class abstract
    virtual void makeSound() = 0;

    void sleep() {
        std::cout << "Sleeping... zzz" << std::endl;
    }
};

// 2. CONCRETE DERIVED CLASS
class Dog : public Animal {
public:
    // Fulfilling the contract by implementing the pure virtual function
    void makeSound() override {
        std::cout << "Woof! Woof!" << std::endl;
    }
};

int main() {
    // -------------------------------------------------------------
    // LINE BELOW WILL FAIL TO COMPILE:
    // Error: cannot declare variable 'myAnimal' to be of abstract type 'Animal'
    // -------------------------------------------------------------
    // Animal myAnimal;

    // -------------------------------------------------------------
    // VALID USAGE:
    // You cannot create an instance, but you CAN use pointers or
    // references of the abstract class type to point to a concrete object.
    // -------------------------------------------------------------
    Animal* polyDog = new Dog();

    polyDog->makeSound(); // Outputs: Woof! Woof!
    polyDog->sleep();     // Outputs: Sleeping... zzz

    delete polyDog;
    return 0;
}

Abstract class example

C++ 
class Shape {
public:
    virtual double area() const = 0;

    virtual ~Shape() = default;
};

Shape defines what derived classes must provide without defining the complete implementation.

C++ 
class Circle : public Shape {
private:
    double radius;

public:
    Circle(double r) : radius(r) {}

    double area() const override {
        return 3.14159 * radius * radius;
    }
};

Abstraction hides unnecessary implementation complexity while exposing a useful interface.

What is a function in C++?

A function is a named block of code that performs a specific operation. It can accept parameters and optionally return a value. Functions help with modularity, code reuse, and readability.

Example:

C++ 
int add(int a, int b) {
    return a + b;
}

Calling:

C++ 
int result = add(10, 20);

What is the difference between a function declaration and definition?

Declaration:

C++ 
int add(int, int);

Definition:

C++ 
int add(int a, int b) {
    return a + b;
}

The declaration tells the compiler about the function.

The definition provides its implementation.

What is function overloading?

Function overloading means defining multiple functions with the same name but different parameter lists. The compiler determines which function to call based on the arguments, so it is compile-time polymorphism.

Example

C++ 
class Calculator {
public:
    int add(int a, int b) {
        return a + b;
    }

    double add(double a, double b) {
        return a + b;
    }

    int add(int a, int b, int c) {
        return a + b + c;
    }
};

Now:

C++ 
Calculator c;

c.add(2, 3);
c.add(2.5, 3.5);
c.add(1, 2, 3);

The compiler chooses the appropriate overload.

What can differ?

Parameters can differ by:

  • Number
  • Type
  • Order

Can we overload a function only by changing its return type?

No.

This is invalid:

C++ 
int getValue();
double getValue();

The compiler cannot distinguish functions based only on return type.

Common trap / wrong answer

Wrong:

Function overloading happens at runtime.

Correct:

Function overloading is resolved at compile time.

What is operator overloading?

Operator overloading allows us to define how an existing operator behaves for user-defined types such as classes.

For example, we can define what + means for two Complex objects.

Example

C++ 
class Complex {
private:
    double real;
    double imag;

public:
    Complex(double r, double i)
        : real(r), imag(i) {}

    Complex operator+(const Complex& other) const {
        return Complex(
            real + other.real,
            imag + other.imag
        );
    }
};

Now:

C++ 
Complex a(2, 3);
Complex b(4, 5);

Complex c = a + b;

The expression:

a + b

uses our overloaded operator+.

Can every operator be overloaded?

No.

Some operators cannot be overloaded, such as:

::

.

.*

?:

sizeof

Common trap / wrong answer

Operator overloading does not create a new operator.

You can only redefine the behavior of operators that C++ already provides, for appropriate user-defined types.

What is an inline function?

An inline function is a function for which the programmer allows the compiler to perform inline substitution, potentially reducing function-call overhead. However, inline does not guarantee that the compiler will actually inline the function.

Example

C++ 
inline int square(int x) {
    return x * x;
}

Calling:

C++ 
int x = square(5);

The compiler may optimize it as if the function body were placed directly at the call site.

Does inline always improve performance?

No.

Inlining can reduce function-call overhead, but excessive inlining can increase code size and potentially hurt instruction-cache behavior.

Modern compilers make their own optimization decisions.

Common trap / wrong answer

❌:

inline guarantees the function will be expanded inline.

Correct:

inline does not guarantee actual inlining.

What is static in C++?

static has different meanings depending on where it is used.

For a local variable, it extends the variable's lifetime to the entire program while preserving local scope. For a class data member, it creates one shared member for the class rather than one copy per object.

A static member function belongs to the class rather than a particular object.

Static local variable

C++ 
void counter() {
    static int count = 0;
    count++;

    cout << count << '\n';
}

Calling:

C++ 
counter();
counter();
counter();

outputs:

1

2

3

The variable retains its value between calls.

Static class member

C++ 
class Student {
public:
    static int count;

    Student() {
        count++;
    }
};

int Student::count = 0;

If we create:

C++ 
Student s1;
Student s2;
Student s3;

there is one shared count, not three separate count variables.

Static member function

C++ 
class Student {
public:
    static int count;

    static void showCount() {
        cout << count;
    }
};

Call:

C++ 
Student::showCount();

No object is required.

Important limitation

A static member function does not have a this pointer because it is not associated with a particular object.

Therefore it cannot directly access non-static members.

Can a static function access a non-static member?

Not directly.

C++ 
class A {
    int x;

public:
    static void fun() {
        // cout << x;  // Error
    }
};

There is no particular object from which to obtain x.

Common trap / wrong answer

Don't say:

Static means the variable is stored on the heap.

That's incorrect.

Storage location is an implementation detail and depends on the context.

Friend Keyword

In C++, the friend keyword is used to grant non-member functions or external classes full access to a class's private and protected members

What is a friend function?

A friend function is a non-member function that is explicitly granted access to a class's private and protected members using the friend declaration.

Example

C++ 
class Box {
private:
    int value;

public:
    Box(int v) : value(v) {}

    friend void printValue(const Box& box);
};

void printValue(const Box& box) {
    cout << box.value;
}

Although printValue() is not a member function, it can access:

box.value

because it is declared as a friend.

Important point

A friend function:

  • Is not a member function
  • Does not have a this pointer
  • Can access private/protected members
  • Must be explicitly declared as a friend

Does friendship get inherited?

No, friendship is not inherited.

Also, friendship is not automatically transitive.

If A is friend of B, that doesn't automatically mean A is friend of C.

Common trap / wrong answer

Don't say:

Friend functions are member functions with special permissions.

They are non-member functions.

What is a friend class?

A friend class is a class that is granted access to the private and protected members of another class.

Example

C++ 
class Engine {
private:
    int power = 100;

    friend class Car;
};

class Car {
public:
    void showEnginePower(const Engine& engine) {
        cout << engine.power;
    }
};

Car can access Engine::power because Car is a friend of Engine.

Is friendship mutual?

No.

If:

C++ 
class A {
    friend class B;
};

then B can access A's private members.

It does not mean A can access B's private members.

Common trap / wrong answer

Friendship should generally be used carefully because it increases coupling between classes.

What is the this pointer?

this is a pointer available inside a non-static member function that points to the object on which the function was called.

Example

C++ 
class Student {
private:
    int age;

public:
    void setAge(int age) {
        this->age = age;
    }
};

Here we have two variables called age:

parameter age

member age

So:

this->age

means the object's member variable.

Example of method chaining

C++ 
class Student {
private:
    int age;

public:
    Student& setAge(int age) {
        this->age = age;
        return *this;
    }
};

Then:

C++ 
Student s;

s.setAge(20).setAge(21);
Important point

this is not available in static member functions because static functions are not associated with a particular object.

What is the type of this?

For a non-const member function of:

C++ 
class A

conceptually:

A* const

For a const member function:

const A* const

The exact type has subtleties, but for a fresher interview, understanding that this points to the current object is the important part.

Common trap / wrong answer

Don't say:

this contains the object's value.

It contains the address of the current object.

What is call by value vs call by reference?

In pass-by-value, the function receives a copy of the argument, so modifying the parameter does not modify the original object.

In pass-by-reference, the function operates on the original object through a reference, so modifications can affect the caller's object.

For read-only large objects

To avoid copying a potentially large object while also preventing the function from modifying it.

Common trap / wrong answer

Don't say:

Pass by reference always passes the address.

That's an implementation-level explanation and isn't the best language-level definition.

A reference provides an alias to the original object.

What is a null pointer?

A pointer that doesn't point to an object/function.

Modern C++:

What is nullptr?

nullptr is the null pointer literal introduced in C++11. It represents a null pointer and has type std::nullptr_t. It is preferred over the old NULL or integer literal 0 because it provides better type safety.

What is const in C++?

const specifies that an object or value cannot be modified through that particular declaration. It can be applied to variables, pointers, references, member functions, parameters, and return types.

Const variable

Pointer to const

const int* p;

int* const p = &x;

Both const

Neither the pointer nor the pointed value can be modified through p.

Const member function

C++ 
class Student {

private:
    int age;
};

Why use const in function parameters?

For example:

  • Function cannot modify name

This is a very common and important C++ pattern.

What are default arguments in C++?

A default argument is a value automatically used by a function when the caller does not provide that argument.

Simple explanation:

You can give a function parameter a default value.

C++ 
void greet(string name = "Dilip") {
    cout << "Hello " << name;
}

greet();          // Hello Dilip
greet("Rahul");   // Hello Rahul

If the argument is not passed, "Dilip" is used.

Important rules:

Default arguments should generally be given from right to left.

C++ 
void fun(int a, int b = 10, int c = 20);  // Valid

But:

C++ 
void fun(int a = 10, int b);  // Invalid

because b has no default value after a defaulted parameter.

Where should default arguments be specified: declaration or definition?

Usually, default arguments are specified in the function declaration, especially when the declaration is in a header file. They generally should not be repeated in the definition.

C++ 
// Declaration
void print(int x, int y = 10);

// Definition
void print(int x, int y) {
    cout << x << " " << y;
}

Then:

C++ 
print(5);       // y = 10
print(5, 20);   // y = 20

What is scope in C++?

Scope defines the region of a program where a name, such as a variable or function, can be accessed.

Simple explanation:

Different types of scope include:

  1. Local/block scope
  2. Function parameter scope
  3. Class scope
  4. Namespace scope
  5. Global scope

Example:

C++ 
int global = 10;  // global scope

void fun() {
    int x = 20;   // local scope

    {
        int y = 30; // block scope
        cout << y;
    }

    // cout << y;  // ❌ y is out of scope
}

What is the difference between scope and lifetime?

Scope tells where a variable can be accessed, while lifetime tells how long the variable exists in memory.

Example:

C++

    int x = 10;
}

x:

  • Lifetime → from its initialization until fun() exits
Important interview point:

Scope and lifetime are related but not the same thing.

A static local variable is a good example:

C++

    static int x = 0;
    x++;
    cout << x;
}

Its scope is inside counter(), but its lifetime is the entire program.

OOP, Constructors & Destructors

What is a constructor?

A constructor is a special member function that is automatically called when an object is created. It is mainly used to initialize the object's state.

Simple explanation:

C++ 
class Student {
    int age;

public:
    Student() {
        age = 20;
    }
};

int main() {
    Student s;  // Constructor automatically called
}

The constructor:

  • Has the same name as the class.
  • Has no return type.
  • Runs automatically during object initialization.
  • Can be overloaded.
What interviewer may ask next:

Can a constructor return a value?

Answer: No. Constructors do not have a return type.

Common trap:

Don't say a constructor "creates memory for the object." Object storage is determined by how the object is created; the constructor initializes the object.

Why do we need constructors?

Constructors ensure that an object starts in a valid and properly initialized state.

Without a constructor:

C++ 
class Account {
    int balance;
};

We could accidentally have an uninitialized balance for a default-initialized object.

With a constructor:

C++ 
class Account {
    int balance;

public:
    Account(int initialBalance) : balance(initialBalance) {}
};

Now:

C++ 
Account a(1000);

The object starts with a valid balance.

What is a default constructor?

A default constructor is a constructor that can be called without arguments.

Example:

C++ 
class Student {
public:
    Student() {
        cout << "Default constructor";
    }
};

Student s;

It can also have default parameters:

C++ 
class Student {
public:
    Student(int age = 18) {}
};

Student s;  // Valid
Important distinction

A default constructor does not necessarily mean a constructor literally written as ClassName().

This is also a default constructor:

C++ 
Student(int age = 18);

because it can be called with no arguments.

What is a parameterized constructor?

A parameterized constructor accepts arguments to initialize an object with specific values.

C++ 
class Student {
    string name;
    int age;

public:
    Student(string n, int a) : name(n), age(a) {}
};

Student s("Dilip", 21);

Each object can have different initial values.

What is constructor overloading?

Constructor overloading means defining multiple constructors with different parameter lists in the same class.

C++ 
class Student {
public:
    Student() {}

    Student(int age) {}

    Student(string name, int age) {}
};

Now:

C++ 
Student a;
Student b(21);
Student c("Dilip", 21);

The compiler chooses the appropriate constructor based on the arguments.

What interviewer may ask next:

Is constructor overloading compile-time polymorphism?

Yes. It is a form of function overloading and therefore compile-time polymorphism.

What is a copy constructor?

A copy constructor creates a new object by copying an existing object of the same class.

Typical form:

C++ 
class Student {
public:
    Student(const Student& other) {
        // copy data
    }
};

Example:

C++ 
Student s1;
Student s2 = s1;

Here s2 is initialized using the copy constructor.

Why const Student&?

Because:

  • We don't want to modify s1.
  • Passing by reference avoids another copy.
  • Passing by value would require copying again.
Common trap:

Copy constructor:

C++ 
Student(const Student&);

Copy assignment:

C++ 
Student& operator=(const Student&);

They are different operations.

What is a move constructor?

A move constructor transfers resources from a temporary or expiring object instead of copying them.

Typical form:

C++ 
class Buffer {
public:
    Buffer(Buffer&& other) {
        // take ownership of other's resources
    }
};

Example:

C++ 
Buffer a;
Buffer b = std::move(a);

Instead of duplicating expensive resources, ownership can be transferred.

Why is this useful?

Suppose an object owns a large dynamically allocated buffer.

Copying:

Object A
   ↓
Large resource

Object B
   ↓
New copy of resource

Moving:

Object A
   ↓
resource ownership transferred
   ↓
Object B

This can significantly improve performance.

Can a constructor be virtual?

No, constructors cannot be virtual.

Reason:

Virtual dispatch requires an already-existing object, but the constructor is responsible for initializing that object.

C++ 
class Base {
public:
    virtual Base() {}   // ❌ Invalid
};
Important interview concept:

Destructors can be virtual, but constructors cannot.

Can a constructor be private?

Yes, a constructor can be private. This is commonly used to control object creation, such as in the Singleton pattern or factory-style designs.

C++ 
class Singleton {
private:
    Singleton() {}

public:
    static Singleton& getInstance() {
        static Singleton obj;
        return obj;
    }
};

External code cannot directly do:

C++ 
Singleton s;  // ❌

because the constructor is private.

Other use cases:

  • Factory methods
  • Controlled object creation
  • Singleton-like designs

What is a delegating constructor?

A delegating constructor calls another constructor of the same class to avoid duplicate initialization logic.

C++ 
class Student {
    string name;
    int age;

public:
    Student() : Student("Unknown", 18) {}

    Student(string n, int a)
        : name(n), age(a) {}
};

Here:

C++ 
Student()

delegates to:

C++ 
Student(string, int)

Benefit:

Avoids duplicating initialization code.

What is an initializer list?

An initializer list initializes data members before the constructor body executes.

C++ 
class Student {
    string name;
    int age;

public:
    Student(string n, int a)
        : name(n), age(a) {
    }
};

The part:

C++ 
: name(n), age(a)

is the initializer list.

Why should we prefer initializer lists?

Initializer lists directly initialize members and are required for certain members such as references, const members, and members without default constructors.

Example:

C++ 
class Example {
    const int x;
    int& ref;

public:
    Example(int value, int& r)
        : x(value), ref(r) {}
};

You cannot properly initialize these members through normal assignment in the constructor body.

Also, for class-type members:

C++ 
class Person {
    string name;

public:
    Person(string n) : name(n) {}
};

The string is directly initialized instead of first being default-constructed and then assigned.

Initialization vs assignment

Initialization:

C++ 
class A {
    int x;

public:
    A(int value) : x(value) {}
};

x is initialized.

Assignment:

C++ 
class A {
    int x;

public:
    A(int value) {
        x = value;
    }
};

x is initialized first and then assigned a new value.

For primitive types the performance difference may be small, but for class-type members it can matter.

Interview answer:

Initialization creates the member with the desired value, while assignment changes the value of an already-existing object.

What is a destructor?

A destructor is a special member function that is automatically called when an object's lifetime ends. It is used for cleanup and resource release.

Syntax:

C++ 
class Student {
public:
    ~Student() {
        cout << "Destructor called";
    }
};

For:

C++ 
Student s;

the destructor is automatically called when s goes out of scope.

Can destructors be overloaded?

No. A class can have only one destructor because a destructor takes no parameters.

Invalid:

C++ 
~Student();
~Student(int x);  // ❌

There is only:

C++ 
~Student();

Can a destructor take parameters?

No. A destructor cannot take parameters and cannot have a return type.

C++ 
~Student();       // ✅
~Student(int x);  // ❌

This is also why destructors cannot be overloaded.

Can a destructor be virtual?

Yes. A destructor can be virtual, and a base class intended for polymorphic use should generally have a virtual destructor.

C++ 
class Base {
public:
    virtual ~Base() {}
};

Why do we need a virtual destructor?

A virtual destructor ensures that deleting a derived object through a base-class pointer calls both the derived and base destructors.

Example:

C++ 
class Base {
public:
    virtual ~Base() {
        cout << "Base destructor\n";
    }
};

class Derived : public Base {
public:
    ~Derived() {
        cout << "Derived destructor\n";
    }
};

int main() {
    Base* ptr = new Derived();
    delete ptr;
}
Output:
Output 
Derived destructor
Base destructor

Without a virtual destructor, deleting a derived object through a base pointer results in undefined behavior.

Very common interview question:

C++ 
Base* p = new Derived();
delete p;

Ask yourself:

Is Base::~Base() virtual?

If yes → proper derived destruction.

What is the constructor/destructor calling order?

Construction happens from base to derived, while destruction happens in the reverse order.

For:

C++ 
class A {};
class B : public A {};
class C : public B {};

Construction:

A → B → C

Destruction:

C → B → A

What is the base constructor vs derived constructor order?

The base class constructor always executes before the derived class constructor.

C++ 
class Base {
public:
    Base() {
        cout << "Base\n";
    }
};

class Derived : public Base {
public:
    Derived() {
        cout << "Derived\n";
    }
};

Creating:

C++ 
Derived d;
Output:
Output 
Base
Derived

What is the base destructor vs derived destructor order?

The derived destructor executes first, followed by the base destructor.

Construction:

Base → Derived

Destruction:

Derived → Base

This guarantees that the derived part of the object is cleaned up before the base portion.

What happens when an exception occurs during construction?

If a constructor throws an exception, the object is considered not successfully constructed, and destructors are called for the already-constructed subobjects and base classes.

What is polymorphism?

Polymorphism means "many forms."

It allows the same interface or operation to behave differently depending on the context or object.

Two major types:

Polymorphism
├── Compile-time
└── Runtime

Examples:

C++ 
add(2, 3);
add(2.5, 3.5);  // overloading

and:

C++ 
Base* p = new Derived();
p->show();       // runtime polymorphism

What is compile-time polymorphism?

Compile-time polymorphism is resolved by the compiler, mainly through function overloading, operator overloading, and templates.

Example:

C++ 
void print(int x) {
    cout << x;
}

void print(string x) {
    cout << x;
}

The compiler determines which print() to call.

What is runtime polymorphism?

Runtime polymorphism occurs when the function to execute is determined at runtime using virtual functions and overriding.

C++ 
class Animal {
public:
    virtual void sound() {
        cout << "Animal sound\n";
    }
};

class Dog : public Animal {
public:
    void sound() override {
        cout << "Bark\n";
    }
};

Animal* a = new Dog();

a->sound();  // Bark

The base pointer points to a derived object, and the overridden function is selected at runtime.

Overloading vs overriding

Overloading Overriding
Same function name Same function signature
Different parameters Derived class provides new implementation
Usually same class Requires inheritance
Compile-time Runtime when virtual
Return type alone cannot overload override keyword recommended

Overloading

C++ 
void add(int a, int b);
void add(double a, double b);

Overriding

C++ 
class Base {
public:
    virtual void show() {}
};

class Derived : public Base {
public:
    void show() override {}
};
Common trap:

Changing only the return type does not create a valid overload.

A virtual function in C++ is a member function declared in a base class using the virtual keyword, which is designed to be overridden by a derived (child) class.

Its primary purpose is to achieve runtime polymorphism.

What is a pure virtual function?

A pure virtual function in C++ is a virtual member function that has no implementation inside the base class, defined by adding = 0 to its declaration. It turns the base class into an abstract class, which means you cannot create objects of that base class directly.

Its main purpose is to create a strict rulebook or interface. It tells anyone writing a child class: "You must provide your own version of this function, or your code will not compile."

What is an abstract class?

An abstract class is a class that cannot be instantiated directly and has at least one pure virtual function.

C++ 
class Shape {
public:
    virtual double area() = 0;
};

This is invalid:

C++ 
Shape s;  // ❌

But this is valid:

C++ 
Shape* s = new Circle();

assuming Circle implements the pure virtual function.

Purpose:

Abstract classes are commonly used to define an interface or common contract for derived classes.

Can an abstract class have a constructor?

Yes. An abstract class can have a constructor, and that constructor is called when a derived-class object is created.

C++ 
class Animal {
public:
    Animal() {
        cout << "Animal constructor\n";
    }

    virtual void sound() = 0;
};

class Dog : public Animal {
public:
    Dog() {
        cout << "Dog constructor\n";
    }

    void sound() override {}
};

Creating:

C++ 
Dog d;

results conceptually in:

Animal constructor

Dog constructor

Can an abstract class have data members?

Yes. An abstract class can have data members, constructors, normal member functions, and pure virtual functions.

C++ 
class Animal {
protected:
    string name;

public:
    Animal(string n) : name(n) {}

    virtual void sound() = 0;
};

The fact that a class is abstract does not mean it cannot contain normal state.

Can we create a pointer to an abstract class?

Yes. We can create a pointer or reference to an abstract class, but we cannot create an object of the abstract class itself.

C++ 
class Shape {
public:
    virtual void draw() = 0;
};

class Circle : public Shape {
public:
    void draw() override {
        cout << "Circle";
    }
};

Shape* ptr = new Circle();  // ✅
ptr->draw();

But:

C++ 
Shape s;  // ❌

Can we call a virtual function from a constructor?

Yes, syntactically we can call a virtual function from a constructor, but virtual dispatch does not call the derived-class override while the base class is being constructed.

Example:

C++ 
class Base {
public:
    Base() {
        show();
    }

    virtual void show() {
        cout << "Base";
    }
};

class Derived : public Base {
public:
    void show() override {
        cout << "Derived";
    }
};
Derived d;
Output:
Output 
Base

Why?

During Base's constructor, the derived portion has not been constructed yet.

So the call behaves as a call to the current construction level.

Very important correction to a common misconception:

Do not say:

"Calling a virtual function in a constructor calls the derived implementation."

It does not.

Can we call a virtual function from a destructor?

Yes, but virtual dispatch is limited to the class whose destructor is currently executing; it does not dispatch to a more-derived class that has already been destroyed.

Example:

C++ 
class Base {
public:
    virtual ~Base() {
        show();
    }

    virtual void show() {
        cout << "Base";
    }
};

class Derived : public Base {
public:
    ~Derived() {
        cout << "Derived destructor\n";
    }

    void show() override {
        cout << "Derived";
    }
};

When destroying a Derived object:

Derived destructor

Base destructor

C++ 
Base::show()

not Derived::show().

Reason:

The derived portion has already been destroyed before the base destructor executes.

What is object slicing?

Object slicing occurs when a derived object is copied into a base object by value, causing the derived-specific part to be sliced off.

Example:

C++ 
class Base {
public:
    int x = 10;
};

class Derived : public Base {
public:
    int y = 20;
};

Derived d;

Base b = d;  // Object slicing

b contains only the Base portion.

The y member is not part of b.

How to avoid it?

Use a reference or pointer:

C++ 
Base& b = d;

or:

C++ 
Base* b = &d;

This is one reason polymorphic objects are commonly handled through references/pointers rather than copied by value.

What is the diamond problem?

The diamond problem occurs in multiple inheritance when a class inherits from two classes that both inherit from the same base class, causing duplicate copies and ambiguity.

Example:

C++ 
class A {
public:
    int x;
};

class B : public A {};
class C : public A {};

class D : public B, public C {};

Structure:

C++ 
       A
      / \
     B   C
      \ /
       D

D contains two copies of A.

So:

C++ 
D d;

// d.x = 10;  // ❌ Ambiguous

The compiler doesn't know whether you mean:

d.B::x

or:

d.C::x

What is virtual inheritance?

Virtual inheritance ensures that only one shared base-class subobject exists when multiple inheritance forms a diamond.

C++ 
class A {
public:
    int x;
};

class B : virtual public A {};
class C : virtual public A {};

class D : public B, public C {};

Now:

C++ 
       A
      / \

virtual virtual

C++ 
    B       C
      \     /
         D

D contains only one shared A subobject.

Therefore:

C++ 
D d;

d.x = 10;  // ✅
Important interview point:

Virtual inheritance solves the duplicate base-subobject/ambiguity problem of the diamond.

It is different from a virtual function.

Composition vs aggregation

Both represent a "has-a" relationship, but composition implies strong ownership and aggregation represents a weaker relationship where the contained object can exist independently.

Composition

C++ 
class Engine {};

class Car {
    Engine engine;
};

The Car owns its Engine as part of its object state.

Conceptually:

Car
 └── Engine

If the Car object is destroyed, its Engine member is destroyed too.

Aggregation

C++ 
class Teacher {};

class Department {
    Teacher* teacher;
};

The teacher can exist independently of the department.

Interview shortcut:
Composition → strong ownership
Aggregation → weak/non-owning relationship

Composition vs inheritance

Inheritance represents an "is-a" relationship, while composition represents a "has-a" relationship.

Inheritance

C++ 
class Dog : public Animal {};

A:

Dog IS-A Animal

Composition

C++ 
class Car {
    Engine engine;
};

A:

Car HAS-A Engine

Example:

Don't use inheritance just because two classes share some code.

Prefer:

C++ 
class Car {
    Engine engine;
};

if the relationship is naturally "has-a."

Why favor composition over inheritance?

Composition usually provides better flexibility, lower coupling, and better encapsulation than inheritance. It allows behavior to be changed by replacing or configuring contained objects rather than creating a rigid inheritance hierarchy.

Suppose:

C++ 
class Car : public Engine {};

This says:

Car IS-A Engine

which is conceptually wrong.

Instead:

C++ 
class Car {
    Engine engine;
};

Now:

Car HAS-A Engine

Main advantages of composition

1. Lower coupling

Classes depend less on a rigid hierarchy.

2. Better flexibility

You can replace the component.

C++ 
class Car {
    unique_ptr<Engine> engine;
};

3. Better encapsulation

Internal implementation can be hidden.

4. Easier testing

You can inject a mock component.

5. Avoids inheritance problems

Such as:

  • Fragile base-class problem
  • Unwanted inherited behavior
  • Deep inheritance hierarchies
  • Tight coupling

Pointers, Memory & Object Lifetime

What is a pointer?

A pointer is a variable that stores the memory address of another object.

C++ 
int x = 10;

int* p = &x;

cout << p;   // address of x
cout << *p;  // 10

Here:

p  → address of x
*p → value stored at that address

NULL vs nullptr

NULL is a legacy null-pointer macro, commonly defined as 0 or 0L, while nullptr is a dedicated C++11 null-pointer literal and is type-safe.

Example:

C++ 
int* p1 = NULL;
int* p2 = nullptr;

Prefer:

C++ 
int* p = nullptr;

Why?

Consider:

C++ 
void fun(int);
void fun(int*);

fun(NULL);

Depending on how NULL is defined, overload resolution can become problematic.

But:

C++ 
fun(nullptr);

clearly selects:

C++ 
fun(int*);

What is a dangling pointer?

A dangling pointer is a pointer that refers to an object whose lifetime has ended.

Example:

C++ 
int* p;

{
    int x = 10;
    p = &x;
}

// x no longer exists

cout << *p;  // ❌ Undefined behavior

Another example:

C++ 
int* p = new int(10);

delete p;

// p is dangling

Safer:

C++ 
delete p;
p = nullptr;

What is a wild pointer?

A wild pointer is an uninitialized pointer that contains an indeterminate value and does not point to a known valid object.

C++ 
int* p;
cout << *p;  // ❌ Undefined behavior

Initialize pointers:

C++ 
int* p = nullptr;

Difference

nullptr pointer → intentionally points to nothing
wild pointer → uninitialized/indeterminate pointer
dangling pointer → previously valid pointer whose target no longer exists

What is a void* pointer?

A void* is a pointer to an object of an unspecified type. It can hold the address of different object types, but it must generally be converted to the appropriate pointer type before dereferencing.

C++ 
int x = 10;

void* p = &x;

int* ip = static_cast<int*>(p);

cout << *ip;

You cannot directly do:

C++ 
void* p = &x;

// cout << *p;  // ❌ Cannot dereference void*
Important:

Modern C++ generally prefers type-safe alternatives such as templates, rather than using void*.

What is a function pointer?

A function pointer stores the address of a function and allows the function to be called indirectly.

Example:

C++ 
int add(int a, int b) {
    return a + b;
}

int (*ptr)(int, int) = add;

cout << ptr(2, 3);  // 5

Here:

C++ 
int (*ptr)(int, int)

means:

ptr is a pointer to a function taking two ints and returning an int.

What is a pointer to pointer?

A pointer to pointer stores the address of another pointer.

C++ 
int x = 10;

int* p = &x;
int** pp = &p;

cout << **pp;  // 10

Think:

x
↑
p
↑
pp
  • pp → address of p
  • *pp → p
  • **pp → x

What is pointer arithmetic?

Pointer arithmetic allows moving a pointer across elements of an array or another contiguous sequence.

Example:

C++ 
int arr[] = {10, 20, 30, 40};

int* p = arr;

cout << *p << '\n';       // 10
cout << *(p + 1) << '\n'; // 20
cout << *(p + 2) << '\n'; // 30

For an int*, p + 1 moves to the next int, not necessarily just one byte.

Conceptually:

p + 1
    ↓
next int-sized element

Valid pointer arithmetic is mainly associated with elements of the same array/object sequence.

Common operations:

C++ 
p++;
p--;
p + n;
p - n;
p1 - p2;

Pointer subtraction is meaningful when the pointers refer to elements of the same array.

What is a pointer to an array?

A pointer to an array points to the entire array object rather than directly to one element.

C++ 
int arr[3] = {10, 20, 30};

int (*p)[3] = &arr;

cout << (*p)[0];  // 10
cout << (*p)[1];  // 20

Notice the parentheses:

C++ 
int (*p)[3];

Without them:

C++ 
int* p[3];

means:

array of 3 pointers.

This is a common interview syntax question.

Can we create an array of references?

No. C++ does not allow arrays of references.

Invalid:

C++ 
int a = 10;
int b = 20;

int& arr[2] = {a, b};  // ❌

Instead, use:

C++ 
int* arr[2] = {&a, &b};

Why can't we have an array of references?

A reference is an alias rather than a standalone object with its own reseatable storage semantics, while array elements must be actual objects/elements with well-defined storage and assignment behavior.

What is Stack Memory?

The stack is memory typically used for function calls and objects with automatic storage duration.

Consider:

C++ 
void fun() {
    int x = 10;
    int y = 20;
}

Conceptually:

Stack

+----------------+
| y = 20         |
+----------------+
| x = 10         |
+----------------+

When fun() starts, the local variables are created.

When fun() ends, their lifetime ends automatically.

fun() starts
     ↓
x and y created
     ↓
fun() executes
     ↓
fun() ends
     ↓
x and y destroyed automatically

You don't write:

C++ 
delete x;

because x wasn't dynamically allocated.

Why is it called "Stack"?

Function calls are typically managed using a call stack.

Suppose:

C++ 
void A() {
    B();
}

void B() {
    C();
}

void C() {
    int x = 10;
}

The call sequence is:

A()
 ↓
B()
 ↓
C()

Conceptually, the stack looks like:

+------------------+
| C() stack frame  |
| x = 10           |
+------------------+
| B() stack frame  |
+------------------+
| A() stack frame  |
+------------------+

When C() finishes:

C() frame removed

Then B() finishes:

B() frame removed

This follows LIFO:

Last In, First Out.

That's why stack-based function-call management is called a stack.

Stack Variable Lifetime

Consider:

C++ 
void fun() {
    int x = 10;

    if (true) {
        int y = 20;
    }

    // y no longer exists here
}

x exists throughout the function:

fun()
┌──────────────────────┐
│ x = 10               │
│                      │
│   if block           │
│   ┌──────────────┐   │
│   │ y = 20       │   │
│   └──────────────┘   │
│                      │
└──────────────────────┘

y has a shorter lifetime because its scope is the if block.

When the block ends:

C++ 
if (true) {
    int y = 20;
} // y's lifetime ends here

y is destroyed automatically.

What is Heap Memory?

The heap, more precisely the free store in C++ terminology, is used for dynamic allocation.

For example:

C++ 
int* p = new int(20);

Here:

p
↓
+----------------+
|      20        |
+----------------+
   dynamic storage

p itself is a local variable, while the int created by new has dynamic storage duration.

Conceptually:

Stack                    Heap / Free Store

+----------+             +----------+
| p        | ----------> | 20       |
+----------+             +----------+

This distinction is extremely important.

p and 20 are not the same thing.

C++ 
int* p = new int(20);
  • p → pointer variable with automatic storage if declared locally
  • *p → dynamically allocated int

Why do we need Dynamic Memory?

Suppose you don't know at compile time how many objects you need.

For example:

C++ 
int n;
cin >> n;

int* arr = new int[n];

Here n is determined at runtime.

The dynamically allocated array has a lifetime independent of the local pointer variable.

However, in modern C++, you generally shouldn't write this manually. Prefer:

C++ 
std::vector<int> arr(n);

The vector manages its dynamic memory automatically.

Consider:

STACK HEAP / FREE STORE

+-----------+                 +-----------+

+-----------+                 +-----------+

is executed:

Heap object destroyed
        ↓
memory returned to allocator

Consider:

What is shallow copy?

Shallow copy copies member values as they are, including pointer values, so two objects may end up pointing to the same resource.

A shallow copy creates a new object that is a copy of an existing object, but does not allocate new memory for any dynamically allocated members. Instead, it copies the values of the members directly. If a member is a pointer, the shallow copy will copy the pointer value (address) rather than the data it points to.

Example:

C++ 
class Buffer {
public:
    int* data;

    Buffer(int value) {
        data = new int(value);
    }
};

Suppose:

C++ 
Buffer a(10);
Buffer b = a;

With a shallow copy:

a.data ──┐
         ↓
       [10]
         ↑
b.data ──┘

Both pointers point to the same memory.

What is deep copy?

Deep copy creates an independent copy of the resource instead of copying only the pointer.

Example:

C++ 
class Buffer {
    int* data;

public:
    Buffer(int value) {
        data = new int(value);
    }

    Buffer(const Buffer& other) {
        data = new int(*other.data);
    }

    ~Buffer() {
        delete data;
    }
};

Now:

C++ 
Buffer a(10);
Buffer b = a;

Conceptually:

a.data → [10]
b.data → [10]

They are two separate allocations.

Why is shallow copy dangerous with raw pointers?

Shallow copying an owning raw pointer can cause multiple objects to own the same resource, leading to double deletion, dangling pointers, and unexpected modifications.

Example:

C++ 
class Buffer {
public:
    int* data;

    Buffer(int value) {
        data = new int(value);
    }

    ~Buffer() {
        delete data;
    }
};

If the compiler-generated copy simply copies the pointer:

C++ 
Buffer a(10);
Buffer b = a;

then:

a.data ──┐
         ↓
        [10]
         ↑
b.data ──┘

When b and a are destroyed, both may try to delete the same memory.

When the objects are destroyed, both destructors execute:

b destroyed
   ↓
delete b.data
   ↓
memory freed

a destroyed
   ↓
delete a.data
   ↓
same memory is freed again

This is called double deletion / double free, leading to undefined behavior.

How do you implement deep copy?

You need to allocate independent storage and copy the value.

C++ 
class Buffer {
    int* data;

public:
    Buffer(int value) {
        data = new int(value);
    }

    Buffer(const Buffer& other) {
        data = new int(*other.data);
    }

    Buffer& operator=(const Buffer& other) {
        if (this != &other) {
            *data = *other.data;
        }
        return *this;
    }

    ~Buffer() {
        delete data;
    }
};

Important components:

copy constructor

copy assignment

destructor

This is directly related to the Rule of 3.

Conceptually, it behaves approximately like:

It copies the pointer value.

It does NOT do:

This is the second question you asked.

Suppose:

C++

    int* data;

        data = new int(value);
    }

        delete data;
    }

Now:

C++

You didn't define:

Conceptually:

C++

Before assignment:

b.data → [20]

After:

            ↓
           [10]
            ↑
b.data ─────┘

Now both point to the same resource.

But there is an additional problem.

The original:

that b.data pointed to is now lost.

Before:

After:

b.data → [10]

[20] has no owner/pointer

That's a memory leak.

Then when both destructors execute, they can attempt to delete the same [10] resource.

Again, undefined behavior.

You need to implement:

For example:

C++

    int* data;

    Buffer(int value) {
        data = new int(value);
    }

    Buffer(const Buffer& other) {
        data = new int(*other.data);
    }

    Buffer& operator=(const Buffer& other) {
        if (this != &other) {
            delete data;
            data = new int(*other.data);
        }

        return *this;
    }

        delete data;
    }
};

Now:

C++

Buffer b(20);

b = a;

produces:

Before:

b.data → [20]

Assignment:

     ↓

     ↓
copy 10

a.data → [10]
b.data → [10]

But these are separate allocations.

C++

This is called self-assignment.

If our assignment operator blindly did:

then after:

would refer to the same freed memory because this == &other.

would access freed memory.

That's undefined behavior.

What is the Rule of 3?

If a class manually manages a resource and defines one of these:

Destructor

Copy constructor

Copy assignment operator

you often need to consider all three.

This is called the Rule of Three.

For our class:

C++ 
class Buffer {
public:
    Buffer(int value);

    Buffer(const Buffer& other);             // 1
    Buffer& operator=(const Buffer& other);  // 2
    ~Buffer();                               // 3
};

Why?

Because all three are related to resource ownership.

If your class owns:

C++ 
int* data;

then you need to carefully define what happens when:

  • an object is copied
  • one object is assigned to another
  • an object is destroyed

What is the Rule of 5?

The Rule of 5 extends the Rule of 3 to include move constructor and move assignment operator.

The five special member functions are:

1. Destructor

2. Copy constructor

3. Copy assignment

4. Move constructor

5. Move assignment

Example:

C++

public:
    Buffer(const Buffer&);
    Buffer& operator=(const Buffer&);

    Buffer(Buffer&&) noexcept;
    Buffer& operator=(Buffer&&) noexcept;

    ~Buffer();
};

The copy constructor is:

C++ 
Buffer(const Buffer& other);

It creates a new object by copying another object.

Example:

C++ 
Buffer b = a;

Copy assignment operator in Rule of 5

The copy assignment operator is:

C++ 
Buffer& operator=(const Buffer& other);

Example:

C++ 
b = a;

The object b already exists.

Destructor in Rule of 5

The destructor:

C++

releases resources owned by the object.

For raw memory:

C++ 
~Buffer() {
    delete[] data;
}

With RAII types like vector and unique_ptr, you usually don't need to write one yourself.

What is the Rule of 0?

The Rule of 0 says that classes should preferably avoid manually managing resources so that they don't need to define these special member functions themselves.

Instead of:

C++

    int* data;
};

prefer:

C++ 
class Buffer {
    vector<int> data;
};

or:

C++ 
class Buffer {
    unique_ptr<int[]> data;
};

Now the resource-owning class handles its own lifetime.

Best modern C++ principle:

Prefer the Rule of 0 whenever possible.

What are move semantics?

Move semantics allow resources to be transferred from one object to another instead of being copied.

Example:

C++ 
vector<int> a(1000000);

vector<int> b = std::move(a);

Instead of copying one million elements, the implementation can transfer ownership of the underlying buffer.

Conceptually:

Before:

a → [large buffer]
b → nothing

After move:

a → valid but moved-from state
b → [large buffer]

Why were move semantics introduced?

Move semantics were introduced to avoid expensive copies of temporary or expiring objects and make resource transfer efficient.

Before move semantics, returning or transferring large resource-owning objects could require expensive copies.

Modern C++ can instead transfer resources.

This is especially useful for:

  • vector
  • string
  • File/resource handles
  • Large buffers
  • Smart pointers

Why should move constructors often be noexcept?

noexcept is a C++ exception specifier that promises a function will not throw any exceptions. [1]

A move constructor is often marked noexcept because standard containers such as std::vector may prefer moving elements during reallocation only when the move operation is known not to throw.

Example:

C++ 
class Buffer {
public:
    Buffer(Buffer&& other) noexcept {
        // transfer resources
    }
};

C++

v.push_back(Buffer());

When the vector needs to reallocate, it wants a safe and efficient way to transfer existing elements.

If moving could throw, the vector may choose copying instead when a suitable copy operation exists, to preserve exception-safety guarantees.

What happens to an object after it is moved from?

A moved-from object remains a valid object, but its value is generally unspecified unless the type documents a stronger post-move state.

Example:

C++ 
string a = "Hello";

string b = std::move(a);

Afterward, a is still a valid std::string, but its exact contents should generally not be relied upon unless specified by the type.

For many standard library types, the object remains in a valid but unspecified state.

Can a moved-from object be used?

Yes. A moved-from object can generally be destroyed, assigned a new value, and used in operations permitted by its type's documented post-move state. You should not assume its old value remains.

Example:

C++ 
string a = "Hello";
string b = std::move(a);

a = "New value";  // ✅
cout << a;        // New value

Avoid assuming:

C++ 
cout << a;

will necessarily print the old "Hello".

Key phrase:

Valid but unspecified state.

Why does vector prefer moving during reallocation when possible?

Suppose:

C++

Conceptually:

Old memory
[ A ][ B ][ C ]

       ↓ reallocation

New memory
[ A ][ B ][ C ]

Moving can transfer resources instead of duplicating them.

But vector also has to preserve exception-safety guarantees. Therefore, if moving isn't noexcept and copying is available, it may prefer copying.

Interview answer:

vector uses move construction when it is safe and advantageous, particularly when the move constructor is noexcept; otherwise it may copy to maintain exception guarantees.

Copy elision is the general concept.

RVO and NRVO are specific situations where copy/move construction can be avoided.

The key idea is:

Instead of creating one object and then copying/moving it into another object, C++ can construct the final object directly where it is needed.

First understand the problem

Consider:

C++ 
class A {
public:
    A() {
        cout << "Constructor\n";
    }

    A(const A&) {
        cout << "Copy constructor\n";
    }

    A(A&&) {
        cout << "Move constructor\n";
    }
};

Now:

C++ 
A create() {
    return A();
}

int main() {
    A obj = create();
}

You might imagine that several objects are involved:

A()
 ↓
temporary object
 ↓
copy/move
 ↓
obj

But C++ can avoid those unnecessary intermediate objects.

Instead:

A()
 ↓
obj

The object is constructed directly as obj.

That's the basic idea behind copy elision.

What exactly is Copy Elision?

Copy elision means:

C++ omits an otherwise unnecessary copy or move construction of an object.

Normally, you might expect:

Object A
   ↓
copy/move
   ↓
Object B

But with copy elision:

Object A/B
   ↓
directly constructed

So instead of:

create object
      ↓
copy it
      ↓
destroy original

C++ can do:

construct final object directly

This can improve performance because it avoids:

  • unnecessary object construction
  • copy construction
  • move construction
  • destruction of temporary objects

What is RVO?

RVO = Return Value Optimization

It is a specific form of copy elision related to returning a temporary/prvalue object from a function.

Consider:

C++ 
A create() {
    return A();
}

And:

C++ 
A obj = create();

The important line is:

C++ 
return A();

A() creates a temporary/prvalue.

You might conceptually imagine:

create()

A()
 ↓
temporary A
 ↓
copy/move
 ↓
obj

But with RVO:

create()

A()
 ↓
obj

The A is constructed directly in the storage associated with obj.

Why is it called Return Value Optimization?

Because the optimization happens around a function's return value.

Example:

C++ 
A create() {
    return A();
}

The function is returning an A.

Instead of:

create A
   ↓
move/copy A
   ↓
caller

C++ can construct the return object directly in the caller's destination.

So:

RVO

Function
   │
   │ return A()
   ↓
Caller
   │
   ↓
obj

NRVO = Named Return Value Optimization

The important word is:

Named

Consider:

C++ 
A create() {
    A obj;
    return obj;
}

Here:

C++ 
A obj;

creates a named local object.

Then:

C++ 
return obj;

returns that named object.

Without NRVO, conceptually:

create()

local obj
   ↓
copy/move
   ↓
returned object
   ↓
caller

With NRVO:

create()

obj
 ↓
constructed directly
 ↓
caller object

So the copy/move can be eliminated.

Why is it called "Named" RVO?

Compare these two:

RVO

    return A();
}

The returned object is a temporary/prvalue.

    A obj;
    return obj;
}

The returned object is a named local variable called obj.

That's where the distinction comes from:

→ return temporary/prvalue

NRVO

→ return named local object

What is RAII?

RAII stands for Resource Acquisition Is Initialization. It ties resource ownership to an object's lifetime: the resource is acquired during initialization and released automatically when the object is destroyed.

Example:

C++ 
class File {
public:
    File() {
        // acquire file resource
    }

    ~File() {
        // release file resource
    }
};

Usage:

C++ 
void process() {
    File file;

    // use file
} // destructor automatically called

The same principle applies to:

  • Memory
  • Files
  • Mutexes
  • Sockets
  • Database connections
  • Locks

Why is RAII important?

RAII makes resource management automatic and exception-safe by tying cleanup to object lifetime.

Without RAII:

C++ 
resource = acquire();

if (error)
    return;  // Could forget cleanup

release(resource);

With RAII:

C++ 
Resource r;

When r goes out of scope, its destructor automatically releases the resource.

Main benefits

  • Automatic cleanup
  • Exception safety
  • Less manual resource management
  • Clear ownership
  • Fewer leaks

How does RAII prevent memory leaks?

Instead of:

C++ 
int* p = new int(10);

and remembering:

C++ 
delete p;

use:

C++ 
auto p = make_unique<int>(10);

When p goes out of scope:

scope ends
   ↓
unique_ptr destructor
   ↓
delete resource

Therefore, even if an exception occurs, cleanup still happens during stack unwinding.

RAII and exception safety

Consider:

C++ 
void process() {
    auto p = make_unique<int>(10);

    throw runtime_error("Error");
}

Even though the function throws:

exception
   ↓
stack unwinding
   ↓
p destructor
   ↓
memory released

This is a major reason RAII is fundamental to C++.

Interview answer:

RAII ensures resources are released automatically during both normal scope exit and exception-driven stack unwinding.

RAII and mutexes

Instead of manually:

C++ 
mutex.lock();

// code

mutex.unlock();

use:

C++ 
lock_guard<mutex> lock(mutex);

When lock goes out of scope:

scope ends
   ↓
lock_guard destructor
   ↓
mutex unlocked

Example:

C++ 
mutex m;
int counter = 0;

void increment() {
    lock_guard<mutex> lock(m);

    counter++;
}

Even if an exception occurs, the mutex is released.

This is RAII.

RAII and file handling

A file wrapper can acquire a file in its constructor and close it in its destructor.

In modern C++, standard library types already apply this idea.

For example:

C++ 
#include <fstream>

void readFile() {
    ifstream file("data.txt");

    // use file

} // file automatically closes

You don't normally need:

C++ 
file.close();

just to ensure cleanup when the object goes out of scope.

Interview answer:

RAII ties the file resource to the lifetime of the stream object, so the file is automatically closed when the stream is destroyed.

Smart Pointers & Modern Memory Management

What are smart pointers?

Smart pointers are C++ objects that manage dynamically allocated resources automatically and release them when they are no longer needed.

Simple explanation

A raw pointer:

C++ 
int* p = new int(10);

delete p;

If we forget delete, we can get a memory leak.

A smart pointer manages the lifetime automatically:

C++ 
auto p = std::make_unique<int>(10);

When p goes out of scope, the memory is automatically released.

The main smart pointers are:

Smart pointer Ownership
unique_ptr Single owner
shared_ptr Multiple owners
weak_ptr Non-owning observer

Code

C++ 
#include <memory>

int main() {
    std::unique_ptr<int> p = std::make_unique<int>(10);
}

No explicit delete is required.

Interviewer may ask

Why is automatic cleanup possible?

Because smart pointers use RAII. Their destructor releases the owned resource.

Common trap

Don't say:

Smart pointers eliminate all memory leaks.

They greatly reduce ownership-related leaks, but incorrect ownership design can still cause leaks, especially with shared_ptr cycles.

Why should we prefer smart pointers over raw owning pointers?

Smart pointers provide automatic ownership and lifetime management, reducing memory leaks, double deletion, and exception-safety problems.

Simple explanation

Raw owning pointer:

C++ 
Resource* r = new Resource();

doSomething();

delete r;

If doSomething() throws an exception, delete r might never execute.

With RAII:

C++ 
auto r = std::make_unique<Resource>();

doSomething();

The destructor of unique_ptr runs during stack unwinding.

Main advantages

  • Automatic cleanup
  • Clear ownership
  • Exception safety
  • Prevents many double-delete errors
  • Easier resource management
  • Expresses ownership in the type
Common trap

Raw pointers are not bad.

The important distinction is:

Prefer smart pointers for ownership; raw pointers are often fine for non-owning observation.

What is unique_ptr?

unique_ptr is a smart pointer that provides exclusive ownership of a dynamically allocated object.

Only one unique_ptr owns the object at a time.

Code

C++ 
#include <memory>

int main() {
    std::unique_ptr<int> p = std::make_unique<int>(10);

    std::cout << *p;
}

When p goes out of scope:

p destroyed
   ↓
owned object deleted
Important property

unique_ptr cannot be copied.

C++ 
std::unique_ptr<int> p1 = std::make_unique<int>(10);

// std::unique_ptr<int> p2 = p1; // ERROR

But it can be moved.

C++ 
std::unique_ptr<int> p2 = std::move(p1);

Now:

p1 → nullptr
p2 → object
Common trap

Don't say unique_ptr means the object can never change ownership.

Ownership can be transferred using move semantics.

What is shared_ptr?

shared_ptr provides shared ownership of an object using reference counting.

Multiple shared_ptrs can own the same object.

Code

C++ 
#include <memory>

auto p1 = std::make_shared<int>(10);

auto p2 = p1;
auto p3 = p1;

Conceptually:

       ┌──────────┐
p1 ───►│          │
p2 ───►│    10    │
p3 ───►│          │
       └──────────┘

use_count = 3

When one owner disappears:

use_count = 2

When the last owner disappears:

object destroyed

Common trap

shared_ptr does not mean "thread-safe object."

Multiple threads can safely manipulate separate shared_ptr instances that share ownership under the standard's atomic-control-block guarantees, but the managed object's data is not automatically thread-safe.

What is weak_ptr?

weak_ptr is a non-owning smart pointer that observes an object managed by shared_ptr without increasing its strong reference count.

Code

C++ 
auto shared = std::make_shared<int>(10);

std::weak_ptr<int> weak = shared;

The weak_ptr observes the object but does not own it.

shared_ptr ───► object
weak_ptr   ───► object

But only the shared_ptr contributes to the strong ownership count.

Why useful?

Most importantly:

weak_ptr helps break shared_ptr ownership cycles.

unique_ptr vs shared_ptr

Feature unique_ptr shared_ptr
Ownership Exclusive Shared
Copyable No Yes
Movable Yes Yes
Reference counting No Yes
Overhead Low Higher
Default choice Usually preferred When shared ownership is required
Interview answer

I prefer unique_ptr by default because it has clear exclusive ownership and lower overhead. I use shared_ptr only when multiple independent owners genuinely need shared lifetime.

Common trap

Don't choose shared_ptr just because multiple parts of the program need access.

If they don't own the object, use a reference or raw pointer for observation.

shared_ptr vs weak_ptr

shared_ptr owns the object and increases the strong reference count, while weak_ptr only observes the object and does not keep it alive.

Example:

C++ 
auto p = std::make_shared<int>(10);

std::shared_ptr<int> p2 = p;
std::weak_ptr<int> w = p;

Conceptually:

shared ownership count = 2

weak observer count = 1

Destroying p:

strong count = 1

Destroying p2:

strong count = 0

object destroyed

The weak_ptr does not prevent this.

Why can't unique_ptr be copied?

Because copying would create two owners of the same resource, violating exclusive ownership.

Suppose copying were allowed:

C++ 
unique_ptr<int> p1(new int(10));
unique_ptr<int> p2 = p1;

Then:

p1 ──┐
     ├──► same object
p2 ──┘

Both would try to delete the same object.

That could cause double deletion.

Therefore:

C++ 
unique_ptr(const unique_ptr&) = delete;

Conceptually.

How do you transfer ownership of unique_ptr?

Ownership is transferred using move semantics with std::move().

C++ 
auto p1 = std::make_unique<int>(10);

auto p2 = std::move(p1);

After this:

p1 → nullptr
p2 → 10
Important

std::move() itself doesn't move the object.

It enables the move constructor/assignment to be selected.

What does std::move(unique_ptr) do?

It converts the unique_ptr into an rvalue so its move constructor or move assignment can transfer ownership.

C++ 
auto p1 = std::make_unique<int>(10);

auto p2 = std::move(p1);

The ownership is transferred by the move operation, not by std::move() itself.

Common trap

Wrong:

std::move() moves the object.

Correct:

std::move() is essentially a cast that enables moving.

How does shared_ptr reference counting work?

shared_ptr maintains a strong reference count representing how many shared_ptrs own the object. When the count reaches zero, the managed object is destroyed.

Example:

C++ 
auto p1 = std::make_shared<int>(10);

auto p2 = p1;
auto p3 = p1;

Conceptually:

p1 ──┐
p2 ──┼──► object
p3 ──┘

strong count = 3

Then:

C++ 
p2.reset();

Count becomes:

2

Then:

C++ 
p3.reset();

Count:

1

Finally:

C++ 
p1.reset();

Count:

0

Object gets destroyed.

What is a control block?

A control block is an internal structure associated with a shared_ptr that stores ownership-related information such as reference counts and usually the deleter.

Conceptually:

             Control Block
          ┌─────────────────┐
          │ strong count    │
          │ weak count      │
          │ deleter         │
          │ other metadata  │
          └────────┬────────┘
                   │
                   ▼
              ┌─────────┐
              │ Object  │
              └─────────┘

Multiple shared_ptrs share the same control block.

Important

The exact implementation details are implementation-dependent, but this is the correct interview-level model.

What is use_count()?

use_count() returns the number of shared_ptr instances that currently share ownership of the same object.

C++ 
auto p1 = std::make_shared<int>(10);

std::cout << p1.use_count(); // 1

auto p2 = p1;

std::cout << p1.use_count(); // 2
Important trap

use_count() counts strong owners, not weak_ptrs.

Also, in multithreaded code, don't use use_count() as a synchronization mechanism.

What happens when the last shared_ptr is destroyed?

When the strong reference count reaches zero, the managed object is destroyed. The control block may remain until all associated weak_ptrs are gone.

Conceptually:

shared_ptr
    ↓
strong count = 0
    ↓
object destroyed

But:

weak_ptr still exists
        ↓
control block may remain

Once there are no strong or weak references requiring the control block, the control block is released.

Why does weak_ptr not increase reference count?

Because weak_ptr is non-owning. If it increased the strong reference count, it could prevent the object from being destroyed.

Example:

C++ 
auto p = std::make_shared<int>(10);

std::weak_ptr<int> w = p;

The weak pointer doesn't keep 10 alive.

When:

C++ 
p.reset();

the object can be destroyed even though w still exists.

What is a circular reference?

A circular reference occurs when objects owned by shared_ptr indirectly or directly own each other, keeping their reference counts above zero forever.

Example:

C++ 
struct B;

struct A {
    std::shared_ptr<B> b;
};

struct B {
    std::shared_ptr<A> a;
};

Now:

C++ 
auto a = std::make_shared<A>();
auto b = std::make_shared<B>();

a->b = b;
b->a = a;

Conceptually:

a ──shared──► b
▲             │
└────shared───┘

Even after external pointers disappear:

strong count of A > 0

strong count of B > 0

So neither object is destroyed.

This causes a memory leak.

How does weak_ptr solve circular references?

Replace one of the owning shared_ptr relationships with a weak_ptr, so the cycle does not keep the objects alive.

Instead of:

C++ 
struct B {
    std::shared_ptr<A> a;
};

use:

C++ 
struct B {
    std::weak_ptr<A> a;
};

Now:

A ──shared──► B
▲             │
└────weak─────┘

The weak edge doesn't increase the strong count.

Therefore, when external owners disappear, both objects can be destroyed.

Typical examples

  • Parent-child relationships
  • Graph structures
  • Observer patterns
  • Caches
  • Bidirectional relationships

What is weak_ptr::lock()?

lock() attempts to obtain a shared_ptr from a weak_ptr. If the object is still alive, it returns a valid shared_ptr; otherwise it returns an empty shared_ptr.

Code

C++ 
auto shared = std::make_shared<int>(10);

std::weak_ptr<int> weak = shared;

if (auto p = weak.lock()) {
    std::cout << *p;
}

If the object is already destroyed:

C++ 
if (auto p = weak.lock()) {
    // object exists
} else {
    // object already destroyed
}

Why use lock()?

You should not simply assume that an observed object is still alive.

lock() safely attempts to create a temporary owning reference.

Prefer:

Instead of:

Yes. The most common case is a circular reference where shared_ptrs keep each other alive.

Example:

Smart pointer as a function parameter

The correct parameter type depends on the ownership semantics.

Case 1 — Function doesn't own object

Prefer reference:

C++ 
void process(const Resource& resource);

or:

C++ 
void process(Resource* resource);

if null is meaningful.

Case 2 — Function takes ownership

Use unique_ptr by value:

C++ 
void process(std::unique_ptr<Resource> resource) {
    // owns resource
}

Call:

C++ 
auto p = std::make_unique<Resource>();

process(std::move(p));

Case 3 — Function shares ownership

Use shared_ptr by value:

C++ 
void process(std::shared_ptr<Resource> resource) {
}

Passing by value means the function participates in shared ownership.

Case 4 — Function only temporarily observes shared-owned object

Usually use:

C++ 
void process(const Resource& resource);

or:

C++ 
void process(const Resource* resource);

rather than unnecessarily passing shared_ptr.

Interview rule

Don't pass a smart pointer merely because the caller happens to have one. Choose the parameter type based on the function's ownership requirement.

Implement a smart pointer

This is a common interview coding question.

A simplified unique_ptr:

C++ 
template <typename T>
class MyUniquePtr {
private:
    T* ptr;

public:
    explicit MyUniquePtr(T* p = nullptr)
        : ptr(p) {}

    ~MyUniquePtr() {
        delete ptr;
    }

    MyUniquePtr(const MyUniquePtr&) = delete;
    MyUniquePtr& operator=(const MyUniquePtr&) = delete;

    MyUniquePtr(MyUniquePtr&& other) noexcept
        : ptr(other.ptr) {
        other.ptr = nullptr;
    }

    MyUniquePtr& operator=(MyUniquePtr&& other) noexcept {
        if (this != &other) {
            delete ptr;

            ptr = other.ptr;
            other.ptr = nullptr;
        }

        return *this;
    }

    T& operator*() const {
        return *ptr;
    }

    T* operator->() const {
        return ptr;
    }

    T* get() const {
        return ptr;
    }
};

Usage:

C++

std::cout << *p;

 ↑
capacity full

        ↓ reallocation

[10][20][30][40][ ][ ]

What happens during vector reallocation?

Suppose:

C++ 
std::vector<int> v;
v.reserve(2);

v.push_back(20);

The vector allocates new storage:

Old storage
[10][20]
   ↓
move/copy
   ↓
New storage
[10][20][30]

Then old storage is released.

Result

Pointers, references, and iterators to elements of the old storage are invalidated.

This is extremely important.

Why is push_back() amortized O(1)?

Short interview answer

Although an individual push_back() can take O(n) during reallocation, capacity grows geometrically, so the total cost over many insertions is O(n), giving O(1) amortized cost per insertion.

Example:

capacity:

1 → 2 → 4 → 8 → 16 ...

Most insertions don't require reallocation.

Only occasional insertions do expensive work.

Therefore:

n push_back operations

≈ O(n) total

per operation

≈ O(1) amortized

Important

Amortized O(1) does not mean every operation is O(1).

What is lambda capture?

Lambda capture specifies which variables from the surrounding scope the lambda can access.

Example:

C++ 
int x = 10;

auto f = [x]() {
    std::cout << x;
};

x is captured.

Important:

parameters → passed when lambda is called
captures   → taken from surrounding scope

Capture by value

Syntax:

[x]

Example:

C++ 
int x = 10;

auto f = [x]() {
    std::cout << x;
};

The lambda stores its own copy of x.

Changing the original:

C++ 
x = 20;

does not change the captured copy.

Common trap

By default, a value-captured variable cannot be modified inside the lambda:

C++ 
int x = 10;

auto f = [x]() {
    // x++; // ERROR
};

Unless the lambda is mutable.

Capture by reference

Syntax:

[&x]

Example:

C++ 
int x = 10;

auto f = [&x]() {
    x++;
};

f();

std::cout << x; // 11

The lambda accesses the original variable.

Important danger

A reference capture can become dangling if the lambda outlives the referenced object.

For example, returning a lambda that captures a local variable by reference is dangerous:

C++ 
auto create() {
    int x = 10;

    return [&x]() {
        return x;
    };
}

After create() returns, x no longer exists.

What is [=]?

[=] captures odr-used local variables from the surrounding scope by value.

Example:

C++

int b = 20;

auto f = [=]() {
    return a + b;
};

The lambda captures the needed local variables by value.

Important

It doesn't mean "copy literally every variable in scope."

Only variables actually needed by the lambda are captured.

What is [&]?

[&] captures odr-used local variables from the surrounding scope by reference.

C++ 
int a = 10;
int b = 20;

auto f = [&]() {
    a++;
    b++;
};

Both refer to the original variables.

Main danger

Lifetime.

If the lambda outlives the referenced variables, the references can dangle.

through the current object.

which captures a copy of the current object rather than capturing the this pointer itself.

This can be useful when the lambda needs its own object state and may outlive the original object.

The lambda's internal copy changes.

What are Concepts in C++?

Concepts are a feature introduced in C++20 that allows us to specify requirements that a type must satisfy before it can be used with a template.

The easiest way to think about concepts is:

A concept is a compile-time rule that says what a template type must be capable of doing.

For example, suppose we write:

C++ 
template <typename T>
void print(T x) {
    cout << x;
}

Here, we're saying:

"Give me any type T."

But that's not really true.

T must support:

C++ 
cout << x;

Otherwise the code won't compile.

A concept lets us explicitly express that requirement.

Why Were Concepts Introduced?

Before C++20, templates were often written like this:

C++ 
template <typename T>
void print(T x) {
    cout << x;
}

It looks like any type can be passed.

For example:

C++ 
print(10);
print("Hello");
print(3.14);

These work because those types can be printed.

But suppose:

C++ 
class Student {
};

and:

C++ 
Student s;
print(s);

There is no:

C++ 
cout << s;

So the compiler generates a complicated template-related error.

Older C++ template errors could become extremely long and difficult to understand.

Concepts allow us to say:

"This template only accepts types satisfying this requirement."

What are C++ casts?

C++ provides four named casts:

  • static_cast
  • dynamic_cast
  • const_cast
  • reinterpret_cast

They are safer and more explicit than C-style casts.

Simple explanation

Each cast has a specific purpose:

Cast Main purpose
static_cast Compile-time conversions
dynamic_cast runtime-checked polymorphic casting
const_cast Add/remove const or volatile
reinterpret_cast Low-level reinterpretation of bits/types

Example:

C++ 
double d = 10.5;

int x = static_cast<int>(d);
What interviewer may ask next

Which cast should you prefer?

Use the most specific C++ cast that expresses your intent. Avoid C-style casts when possible.

Common trap

Don't say that all four casts perform the same type of conversion.

What is static_cast?

static_cast performs compile-time conversions when the conversion is known to be valid.

Simple explanation

Common uses:

C++ 
double d = 10.5;
int x = static_cast<int>(d);

It can also be used for certain inheritance conversions:

C++ 
class Base {};
class Derived : public Base {};

Derived d;
Base* b = static_cast<Base*>(&d);

It can also convert numeric types, enums, and other explicitly allowed conversions.

Code example

C++ 
int x = 10;
double y = static_cast<double>(x);

std::cout << y;
Common trap

static_cast does not perform runtime checking for a downcast.

C++ 
Base* b = ...;

Derived* d = static_cast<Derived*>(b);

This is only safe if b actually points to a suitable Derived object.

What is dynamic_cast?

dynamic_cast performs runtime-checked casting, mainly within polymorphic inheritance hierarchies.

Simple explanation

Consider:

C++ 
class Base {
public:
    virtual ~Base() = default;
};

class Derived : public Base {
public:
    void show() {
        std::cout << "Derived\n";
    }
};

Now:

C++ 
Base* base = new Derived;

Derived* derived = dynamic_cast<Derived*>(base);

if (derived) {
    derived->show();
}

The runtime checks whether the object is actually a Derived.

Important requirement

For downcasting through a base pointer/reference, the base class generally needs to be polymorphic, meaning it has at least one virtual function.

Common trap

Don't say:

"dynamic_cast is always better than static_cast."

It performs runtime checking and has overhead. Use it when runtime type checking is actually needed.

What is const_cast?

const_cast is used to add or remove const or volatile qualification.

Example

C++ 
const int x = 10;

int* p = const_cast<int*>(&x);

But this does not make it safe to modify x.

C++ 
*p = 20;  // Undefined behavior

because x was originally declared const.

Safe example

C++ 
int x = 10;

const int* p = &x;

int* q = const_cast<int*>(p);

*q = 20;  // OK

The original object was not actually const.

Common trap

const_cast does not magically make a genuinely const object mutable.

const_cast is used to add or remove const or volatile qualification.

Example

C++

But this does not make it safe to modify x.

because x was originally declared const.

Safe example

C++

const_cast does not magically make a genuinely const object mutable.

What is reinterpret_cast?

reinterpret_cast performs low-level reinterpretation of one type as another type. It should be used very carefully because incorrect use can lead to undefined behavior.

Example

C++ 
int x = 10;

int* p = &x;

std::uintptr_t address =

C++ 
    reinterpret_cast<std::uintptr_t>(p);

It is commonly associated with low-level systems programming, memory addresses, hardware interfaces, and interoperability.

Why dangerous?

It does not make the underlying object magically become another valid object type.

For example:

C++ 
double d = 10.5;

int* p = reinterpret_cast<int*>(&d);

Dereferencing p as an int can violate object/lifetime/alignment/aliasing rules.

Common trap

Don't describe it as simply:

"It converts any type safely."

It is exactly the opposite: it is a low-level, potentially unsafe operation.

C-style cast vs C++ casts

C-style casts are less explicit because they can attempt several kinds of conversions. C++ casts clearly express the programmer's intent and are easier to review.

C-style:

C++ 
int x = (int)3.14;

C++:

C++ 
int x = static_cast<int>(3.14);

Why prefer C++ casts?

They:

  • clearly communicate intent
  • are easier to search for
  • provide more restricted conversions
  • make dangerous conversions more obvious
Common trap

Don't say C-style casts are always equivalent to static_cast.

A C-style cast can attempt combinations involving const_cast, static_cast, and reinterpret_cast depending on the types.

When should dynamic_cast be used?

Use dynamic_cast when you genuinely need to determine or safely convert the runtime type within a polymorphic hierarchy.

Example

    virtual ~Base() = default;

    void meow() {
        std::cout << "Meow\n";
    }
};

void process(Base* obj) {
    if (Dog* dog = dynamic_cast<Dog*>(obj)) {

}

For a pointer cast, it returns nullptr.

No.

Yes.

class Base {

    virtual void show() = 0;

A pure virtual function can define an interface while also providing common base behavior.

A destructor can be declared pure virtual to make the class abstract, but it still needs a definition.

C++ 
class Base {
public:
    virtual ~Base() = 0;
};

}

When a derived object is destroyed, the base destructor is eventually called.

is still required.

override tells the compiler that a derived function is intended to override a virtual function from the base class.

C++ 
class Base {
public:
    virtual void show();
};

class Derived : public Base {
public:
    void show() override;
};

If the function doesn't actually override a base virtual function, the compiler reports an error.

Why useful?

It catches mistakes such as:

C++ 
void show(int x) override;

when the base has:

C++ 
virtual void show();

Derived* derived =

C++ 
    dynamic_cast<Derived*>(base);

It is potentially unsafe because the base pointer might not actually refer to a Derived object.

Upcasting

Derived → Base

Usually safe.

Downcasting

Base → Derived

Requires validation or a guarantee about the actual object.

What is safe downcasting?

dynamic_cast provides runtime-checked downcasting in a polymorphic hierarchy.

C++ 
Base* base = new Derived;

Derived* derived =

C++ 
    dynamic_cast<Derived*>(base);

if (derived) {
    derived->show();
}

If base does not point to a Derived, the pointer becomes nullptr.

Compared with static_cast

C++ 
Derived* d = static_cast<Derived*>(base);

static_cast does not perform the same runtime check.

Example: Downcasting fails

C++ 
#include <iostream>
using namespace std;

class Base {
public:
    virtual ~Base() = default;
};

class Derived : public Base {
public:
    void show() {
        cout << "Derived object\n";
    }
};

int main() {

    // This object is actually a Base object
    Base* b2 = new Base;

    // Try to downcast Base* to Derived*
    Derived* d = dynamic_cast<Derived*>(b2);

    if (d == nullptr) {
        cout << "Downcasting failed\n";
    } else {
        d->show();
    }

    delete b2;
}
Output
Output 
Downcasting failed

Why does it fail?

Look at this line:

C++ 
Base* b2 = new Base;

The actual object is:

b2
 ↓
┌──────────────┐
│ Base object  │
└──────────────┘

It is not a Derived object.

Then we ask:

C++ 
Derived* d = dynamic_cast<Derived*>(b2);

dynamic_cast checks the actual runtime type:

Base* b2
   │
   ▼
Actual object
   │
   ▼
Base
   │
   ✗
   │
   ▼

Derived?

The answer is no, so:

d == nullptr

Compare with successful downcasting

C++ 
Base* b1 = new Derived;

Derived* d = dynamic_cast<Derived*>(b1);

Here:

b1
 ↓
┌────────────────┐
│ Derived object │
└────────────────┘

So:

Base* b1
   │
   ▼
Actual object = Derived
   │
   ✓
   │
   ▼
Derived*

Therefore:

d != nullptr

The key point

The pointer type is Base* in both cases:

C++ 
Base* b1 = new Derived;
Base* b2 = new Base;

But the actual object type is different:

b1 → Derived object → downcast succeeds
b2 → Base object → downcast fails

This is exactly why dynamic_cast is useful: it checks the actual runtime object type rather than blindly assuming the cast is valid.

Threads

1. What is a thread?

Short interview answer

A thread is the smallest unit of execution within a process. Threads in the same process share resources such as memory, while each thread has its own execution state and stack.

Simple explanation

A process can contain multiple threads:

Process
├── Thread 1 → stack
├── Thread 2 → stack
├── Thread 3 → stack
│
└── Shared heap / global data

Threads share:

  • heap
  • global/static variables
  • code
  • open resources

Each thread typically has its own:

  • stack
  • registers
  • program counter
Common trap

Don't say threads have completely separate memory. Threads within the same process share the process's address space.

2. Process vs Thread

Short interview answer

A process is an independent execution environment with its own address space, while threads are execution units within a process and share its address space.

Process Thread
Separate address space Shares process address space
More expensive to create Usually cheaper
Communication needs IPC mechanisms Can communicate through shared memory
Failure usually isolated One thread can affect the whole process
Has one or more threads Exists inside a process
Interview point

Threads make communication easier but introduce synchronization problems.

3. How do you create a thread in C++?

Short interview answer

Use std::thread from the <thread> header.

C++ 
#include <thread>
#include <iostream>

void work() {
    std::cout << "Working\n";
}

int main() {
    std::thread t(work);

    t.join();
}
Important

The main thread and t execute concurrently when the scheduler allows it.

4. What is std::thread?

Short interview answer

std::thread is the standard C++ class used to represent and manage a thread of execution.

It can execute:

  • functions
  • lambdas
  • function objects
  • member functions

Example:

C++ 
std::thread t([] {
    std::cout << "Hello\n";
});

t.join();
Common trap

Creating a std::thread doesn't mean the work is automatically synchronized with the main thread. You must manage its lifetime.

5. What is join()?

Short interview answer

join() makes the calling thread wait until the target thread finishes execution.

C++ 
std::thread t(work);

t.join();

std::cout << "Thread finished\n";

The output after join() executes is guaranteed to occur after work() finishes.

Important

A thread can be joined only once.

6. What is detach()?

Short interview answer

detach() separates the thread from the std::thread object, allowing the thread to continue independently.

C++ 
std::thread t(work);

t.detach();

After detaching, the std::thread object no longer represents the running thread.

Danger

You lose direct control over its lifetime.

For example, this is dangerous:

C++ 
void start() {
    int x = 10;

    std::thread t([&] {
        std::cout << x;
    });

    t.detach();
}

x may be destroyed while the detached thread still accesses it.

Interview point

Prefer join() when you need clear lifetime management.

7. What is joinable()?

Short interview answer

joinable() tells whether a std::thread object currently represents a thread of execution.

C++ 
std::thread t(work);

if (t.joinable()) {
    t.join();
}

A default-constructed thread is not joinable:

C++ 
std::thread t;

std::cout << t.joinable();  // false

After join() or detach(), it is also no longer joinable.

8. What happens if a joinable thread is destroyed?

Short interview answer

If a std::thread object is destroyed while it is still joinable, the program calls std::terminate().

Example:

C++ 
{
    std::thread t(work);
} // std::terminate()

Correct approach

C++ 
{
    std::thread t(work);

    t.join();
}

or:

C++ 
{
    std::thread t(work);

    t.detach();
}
Important interview point

This behavior exists to prevent silently abandoning a running thread.

9. Passing arguments to a thread

Example

C++ 
void add(int a, int b) {
    std::cout << a + b;
}

std::thread t(add, 10, 20);

t.join();

Arguments are passed to the callable when the thread is created.

Lambda example

C++ 
int x = 10;

std::thread t([x] {
    std::cout << x;
});

t.join();
Important

Arguments are generally stored/decayed inside the thread's internal state. Special handling is needed when you want to pass references.

10. Passing by reference using std::ref

Suppose:

C++ 
void increment(int& x) {
    ++x;
}

This won't work as a normal copied argument when you intend reference semantics.

Use:

C++ 
int x = 10;

std::thread t(increment, std::ref(x));

t.join();

std::cout << x; // 11

Why std::ref?

It creates a reference wrapper that tells the thread machinery to pass the original object by reference.

Common trap

The referenced object must remain alive while the thread accesses it.

Race Conditions

11. What is a race condition?

Short interview answer

A race condition occurs when the program's result depends on the timing or ordering of concurrent operations.

Example:

C++ 
int counter = 0;

void increment() {
    ++counter;
}

Two threads executing this simultaneously can produce unexpected results.

Why?

Conceptually:

Thread 1: read counter

Thread 2: read counter

Thread 1: increment

Thread 2: increment

Thread 1: write

Thread 2: write

An update can be lost.

12. What is a data race?

Short interview answer

A data race occurs when multiple threads access the same memory location concurrently, at least one access is a write, and the accesses are not properly synchronized.

In C++, a data race results in undefined behavior.

Example:

C++ 
int counter = 0;

void work() {
    ++counter;
}

If two threads execute work() concurrently without synchronization, there is a data race.

Very important
Data race → Undefined behavior

13. Race condition vs data race

This is a very common interview question.

Race condition

A broader concept where correctness depends on execution timing.

Data race

A specific concurrent memory-access problem that violates the language's synchronization rules and causes undefined behavior in C++.

Example

Two threads may race to perform operations where the final result depends on ordering, even if the accesses themselves are synchronized.

So:

Data race ⊂ race-condition-related problems

Not every race condition is necessarily a C++ data race.

14. How do you prevent a data race?

Short interview answer

Use proper synchronization or avoid shared mutable state.

Common techniques:

  • std::mutex
  • std::atomic
  • immutable data
  • thread-local data
  • message passing

Mutex example

C++ 
std::mutex m;
int counter = 0;

void increment() {
    std::lock_guard<std::mutex> lock(m);
    ++counter;
}

Now only one thread at a time modifies counter.

15. What is thread safety?

Short interview answer

Thread safety means code behaves correctly when accessed concurrently by multiple threads.

Example:

C++ 
class Counter {
    std::mutex m;
    int value = 0;

public:
    void increment() {
        std::lock_guard<std::mutex> lock(m);
        ++value;
    }
C++ 
};

Multiple threads can safely call increment().

Important

Thread-safe doesn't necessarily mean lock-free or highly performant.

16. What is shared state?

Short interview answer

Shared state is data that can be accessed by multiple threads.

Examples:

C++ 
int counter;
std::vector<int> data;
std::unordered_map<int, int> cache;

If multiple threads modify shared state, synchronization may be required.

Better design

Reduce shared mutable state whenever possible.

17. What is a mutex?

Short interview answer

A mutex, or mutual exclusion lock, ensures that only one thread at a time can enter a protected critical section. 

Thread 1 ──┐
           ↓
         Mutex
           ↓
       Critical
        Section
           ↑
Thread 2 ──┘

18. What is std::mutex?

Short interview answer

std::mutex is the standard C++ mutual exclusion primitive used to protect shared data.

C++ 
std::mutex m;
int counter = 0;

void increment() {
    std::lock_guard<std::mutex> lock(m);
    ++counter;
}

19. What does lock() do?

Short interview answer

lock() acquires the mutex. If another thread already owns it, the calling thread waits until it becomes available.

C++ 
m.lock();

counter++;

m.unlock();

Problem

Manual locking is easy to get wrong.

20. What does unlock() do?

Short interview answer

unlock() releases the mutex so another waiting thread can acquire it.

C++ 
m.lock();

counter++;

m.unlock();
Danger

If an exception occurs before unlock():

C++ 
m.lock();

someFunction(); // throws

m.unlock();    // never reached

The mutex may remain locked.

That's why RAII wrappers are preferred.

21. What is std::lock_guard?

Short interview answer

std::lock_guard is a simple RAII wrapper that locks a mutex when constructed and unlocks it when destroyed.

C++ 
std::mutex m;

void work() {
    std::lock_guard<std::mutex> lock(m);

    // critical section
}

When lock goes out of scope:

constructor → lock()
destructor  → unlock()

Main advantage

It automatically unlocks even when exceptions occur.

22. What is std::unique_lock?

Short interview answer

std::unique_lock is a flexible RAII mutex wrapper that supports operations such as deferred locking, manual unlock/relock, and interaction with condition variables.

Example:

C++ 
std::unique_lock<std::mutex> lock(m);

counter++;

lock.unlock();

// do other work

lock.lock();

It can also defer locking:

C++ 
std::unique_lock<std::mutex> lock(m, std::defer_lock);

lock.lock();
Key idea

More flexible than lock_guard, but has slightly more overhead/complexity.

23. What is std::scoped_lock?

Short interview answer

std::scoped_lock is an RAII locking wrapper that can lock one or multiple mutexes safely.

Example:

C++ 
std::scoped_lock lock(m1, m2);

It is especially useful when multiple mutexes must be acquired together.

Important

It uses a deadlock-avoidance algorithm for multiple mutexes.

24. lock_guard vs unique_lock

lock_guard unique_lock
Simple Flexible
Locks immediately Can defer locking
Cannot manually unlock/relock Can unlock/relock
Low overhead More state/overhead
Good for simple critical sections Required/useful for condition variables
Interview answer

Use lock_guard when you simply need scoped locking. Use unique_lock when you need more control over the lock's lifetime or condition variables.

25. unique_lock vs scoped_lock

unique_lock

Best when you need:

  • deferred locking
  • unlock/relock
  • condition variables
C++ 
std::unique_lock<std::mutex> lock(m);

scoped_lock

Best when you want to acquire multiple mutexes together:

C++ 
std::scoped_lock lock(m1, m2);

Simple distinction

unique_lock  → flexibility
scoped_lock  → convenient safe locking of multiple mutexes

26. Why is RAII important for mutexes?

Short interview answer

RAII ensures the mutex is automatically released when the lock object leaves scope, even if an exception occurs.

C++ 
{
    std::lock_guard<std::mutex> lock(m);

    // critical section
}

Conceptually:

enter scope
   ↓
lock
   ↓
critical section
   ↓
leave scope
   ↓
unlock automatically

This prevents many lock-leak bugs.

27. Why is manual lock/unlock dangerous?

Consider:

C++ 
m.lock();

doSomething();

m.unlock();

If doSomething() throws:

lock()
  ↓
exception
  ↓
unlock() never runs
  ↓
mutex remains locked

Other threads can block indefinitely.

Better:

C++ 
std::lock_guard<std::mutex> lock(m);
doSomething();

Deadlocks

28. What is a deadlock?

Short interview answer

A deadlock occurs when two or more threads wait indefinitely for resources held by each other.

Example:

Thread 1:

locks A

waits for B

Thread 2:

locks B

waits for A

Neither can continue.

29. What are the four Coffman conditions?

A deadlock requires these four conditions:

1. Mutual exclusion

A resource can be held by only one thread at a time.

2. Hold and wait

A thread holds one resource while waiting for another.

3. No preemption

Resources cannot be forcibly taken away.

4. Circular wait

There is a circular chain of waiting.

T1 → waits for resource held by T2
T2 → waits for resource held by T1
Interview trick

Breaking any one of the four conditions can prevent deadlock.

30. How can deadlocks be prevented?

Common techniques:

  • consistent lock ordering
  • acquire multiple locks atomically
  • use std::scoped_lock
  • use std::lock
  • minimize lock scope
  • avoid unnecessary nested locks
  • use try_lock with appropriate retry/backoff strategies

Most common answer

Establish a consistent global ordering for acquiring locks.

31. What is lock ordering?

Suppose there are:

C++ 
std::mutex A;
std::mutex B;

Always acquire:

A → B

Never:

Thread 1: A → B
Thread 2: B → A

Because that can create:

T1 holds A → waits for B
T2 holds B → waits for A

Instead, all threads follow:

A → B

32. What is std::lock?

Short interview answer

std::lock locks multiple mutexes using a deadlock-avoidance algorithm.

Example:

C++ 
std::lock(m1, m2);

std::lock_guard<std::mutex> l1(m1, std::adopt_lock);
std::lock_guard<std::mutex> l2(m2, std::adopt_lock);

Modern alternative

Usually simpler:

C++ 
std::scoped_lock lock(m1, m2);

33. What is std::scoped_lock for deadlock prevention?

For multiple mutexes:

C++ 
std::scoped_lock lock(m1, m2);

It acquires them using a deadlock-avoidance strategy.

This is preferable to manually doing:

C++ 
m1.lock();
m2.lock();

because different threads could acquire them in opposite orders.

34. What is try_lock?

Short interview answer

try_lock() attempts to acquire a mutex without blocking indefinitely.

C++ 
if (m.try_lock()) {
    // acquired
    m.unlock();
} else {
    // couldn't acquire
}

For multiple locks, std::try_lock can also be used.

Use case

Useful when the program cannot afford to wait indefinitely or wants to perform another action if the lock isn't immediately available.

35. Deadlock vs starvation vs livelock

Deadlock

Threads wait forever for each other.

T1 → waits for T2
T2 → waits for T1

Starvation

A thread keeps getting denied access to a resource while others continue making progress.

T1 → repeatedly gets lock
T2 → keeps waiting

Livelock

Threads are active but keep responding to each other without making progress.

T1 → backs off
T2 → backs off
T1 → retries
T2 → retries

...

Easy memory trick
Deadlock   → stuck waiting
Starvation → never gets chance
Livelock   → moving but not progressing

Atomic

36. What is std::atomic?

Short interview answer

std::atomic provides atomic operations on shared data, allowing certain operations to occur without a data race.

Example:

C++ 
std::atomic<int> counter{0};

void increment() {
    ++counter;
}

Multiple threads can safely increment it.

Important

Atomic does not automatically make a larger multi-step operation atomic.

37. Atomic vs mutex

Atomic Mutex
Good for simple shared values Good for complex shared state
Supports atomic operations Protects critical sections
Often lower overhead May involve blocking
Can support lock-free implementations Usually uses locking
More difficult for complex invariants Easier for multi-variable consistency

Example

Atomic:

C++ 
std::atomic<int> counter;
counter++;

Mutex:

C++ 
std::lock_guard<std::mutex> lock(m);

balance -= amount;
log.push_back(amount);

If multiple pieces of state must change together, a mutex is often the better abstraction.

38. When should you use atomic?

Short interview answer

Use std::atomic when shared state can be correctly represented through atomic operations, such as counters, flags, or simple state variables.

Example:

C++ 
std::atomic<bool> stop{false};

Worker:

C++ 
while (!stop.load()) {
    // work
}

Another thread:

C++ 
stop.store(true);
Common trap

Don't replace every mutex with an atomic.

39. What is load()?

Short interview answer

load() atomically reads the value of an atomic object.

C++ 
std::atomic<int> x{10};

int value = x.load();

You can specify memory ordering:

C++ 
x.load(std::memory_order_relaxed);

40. What is store()?

Short interview answer

store() atomically writes a value to an atomic object.

C++ 
std::atomic<int> x{10};

x.store(20);

Memory ordering can also be specified.

41. What is fetch_add()?

Short interview answer

fetch_add() atomically adds a value and returns the previous value.

C++ 
std::atomic<int> counter{10};

int old = counter.fetch_add(5);

Afterward:

old = 10

counter = 15

It is useful for thread-safe counters.

42. What is compare_exchange?

Short interview answer

compare_exchange atomically compares an atomic value with an expected value and replaces it with a desired value if they match.

Example:

C++ 
std::atomic<int> x{10};

int expected = 10;

bool success =
    x.compare_exchange_strong(expected, 20);

If x == expected:

x becomes 20

success = true

If not:

success = false

expected = actual x

43. What is CAS?

Short interview answer

CAS means Compare-And-Swap or Compare-And-Exchange.

Conceptually:

C++ 
if (current == expected)
    current = desired;
else
    fail

The operation happens atomically.

Common use

CAS is a fundamental building block for lock-free algorithms.

44. What is lock-free programming?

Short interview answer

Lock-free programming uses atomic operations to coordinate threads without traditional mutex locks, with the guarantee that system-wide progress is made even if individual threads are delayed.

Example idea

C++ 
while (true) {
    int old = value.load();

    if (value.compare_exchange_weak(old, old + 1))
        break;
}
Important distinction

Lock-free does not mean wait-free.

Lock-free guarantees some thread makes progress.

Wait-free aims to guarantee that every operation completes within a bounded number of steps.

45. What is memory ordering?

Short interview answer

Memory ordering controls how atomic operations synchronize and how memory accesses are ordered between threads.

C++ provides different memory-ordering guarantees.

Common ones:

relaxed

acquire

release

acq_rel

seq_cst

For interviews, understand:

relaxed → atomicity only
acquire → prevents later operations from moving before acquire
release → prevents earlier operations from moving after release

46. What is memory_order_relaxed?

Short interview answer

memory_order_relaxed guarantees atomicity of the atomic operation but provides no synchronization ordering with other memory accesses.

Example:

counter.fetch_add(

C++ 
    1,
    std::memory_order_relaxed
);

Good for independent counters where you don't need to publish other data.

Key idea

Atomic? Yes

Synchronization? No

47. What is memory_order_acquire?

Short interview answer

An acquire operation prevents subsequent memory operations from being reordered before it and can synchronize with a corresponding release operation.

Typical pattern:

C++ 
ready.load(std::memory_order_acquire);

If it observes a value stored with release, writes before the release become visible after the acquire.

48. What is memory_order_release?

Short interview answer

A release operation prevents preceding memory operations from being reordered after it and can publish those operations to a thread performing a corresponding acquire.

Example:

C++ 
data = 42;

ready.store(

C++ 
    true,
    std::memory_order_release
);

Another thread:

C++ 
if (ready.load(std::memory_order_acquire)) {
    std::cout << data;
}

The release/acquire pair establishes the required synchronization when the acquire observes the released value.

49. Acquire vs release

The easiest way to remember:

Thread 1                         Thread 2

data = 42
   |
   ↓
release store  ───────────────→ acquire load
                                  |
                                  ↓
                              read data

Release

Publishes previous writes.

Acquire

Makes those published writes visible to the acquiring thread.

Interview answer

Release is generally used when publishing data; acquire is used when consuming that published data.

50. What is condition_variable?

Short interview answer

std::condition_variable allows a thread to sleep until another thread signals that some condition or state may have changed.

It is commonly used with:

  • std::mutex
  • std::unique_lock

Example:

C++ 
std::mutex m;
std::condition_variable cv;

bool ready = false;

void worker() {
    std::unique_lock<std::mutex> lock(m);

        return ready;
    });
}

C++ 
{
    std::lock_guard<std::mutex> lock(m);
    ready = true;
}

cv.notify_one();

51. What is the producer-consumer problem?

Short interview answer

The producer-consumer problem involves one or more threads producing data into a shared buffer and other threads consuming it safely.

Producer
   ↓
[ Shared Queue ]
   ↓
Consumer

The queue must be protected against:

  • simultaneous modification
  • consuming from an empty queue
  • overflowing a bounded queue

Typical solution

Use:

mutex
+
condition_variable
+
queue

Example:

C++ 
std::queue<int> q;
std::mutex m;
std::condition_variable cv;

Producer:

C++ 
{
    std::lock_guard<std::mutex> lock(m);
    q.push(10);
}

cv.notify_one();

Consumer:

C++ 
std::unique_lock<std::mutex> lock(m);

cv.wait(lock, [] {
    return !q.empty();
});

int value = q.front();
q.pop();

52. notify_one() vs notify_all()

C++ 
notify_one()

Wakes one waiting thread.

C++ 
cv.notify_one();

Useful when one newly available resource can be consumed by one worker.

C++ 
notify_all()

Wakes all waiting threads.

C++ 
cv.notify_all();

All awakened threads re-check the condition.

Interview point

notify_all() can cause many threads to wake even though only one can proceed, creating unnecessary contention.

53. Why use a predicate with condition_variable?

Instead of:

C++ 
cv.wait(lock);

prefer:

C++ 
cv.wait(lock, [] {
    return !q.empty();
});

Why?

Because waking up does not necessarily mean the desired condition is true.

The predicate effectively behaves like:

C++ 
while (!condition) {
    wait();
}

This handles spurious wakeups and state changes correctly.

54. What are spurious wakeups?

Short interview answer

A spurious wakeup occurs when a thread waiting on a condition variable wakes up even though no notification corresponding to its desired condition occurred.

Therefore:

C++ 
cv.wait(lock);

does not mean:

"The condition is definitely true."

Instead, always check the condition again.

Preferred:

C++ 
cv.wait(lock, [] {
    return ready;
});

Conceptually:

C++ 
while (!ready) {
    cv.wait(lock);
}
Common trap

Never write synchronization logic assuming that one notify_one() or notify_all() guarantees the condition is true.

1. What is auto?

Short interview answer

C++ 
auto x = 10;       // int

auto name = "Bob"; // const char*

The type is still statically known; auto does not make C++ dynamically typed.

Common trap
C++ 
auto x;

is invalid because there is no initializer from which to deduce the type.

2. What is decltype?

Short interview answer

decltype obtains the type of an expression without evaluating that expression.

C++ 
int x = 10;

decltype(x) y = 20;

Here:

decltype(x) → int
Important difference

decltype follows special rules for value categories.

C++ 
int x = 10;

decltype(x)  a = x;  // int
decltype((x)) b = x; // int&

Why?

x → unparenthesized variable → declared type int
(x) → lvalue expression → int&

This distinction is frequently tested.

3. auto vs decltype

auto decltype

            newData[i] = data[i];

        delete[] data;
        data = newData;
        cap = newCap;
    }

public:
    DynamicArray() : data(new int[2]), sz(0), cap(2) {}

    void push_back(int x) {
        if (sz == cap)
            grow();

        data[sz++] = x;
    }

    int& operator[](size_t i) {
        return data[i];
    }

    size_t size() const {
        return sz;
    }

    ~DynamicArray() {
        delete[] data;
    }
};

Interviewer may ask: What is push_back() complexity?

Answer: Amortized O(1), because resizing happens occasionally.

Trap: A real vector also handles constructors, exceptions, allocators, iterators, move semantics, etc.

16. Implement a circular queue

The important idea is:

rear = (rear + 1) % capacity

front = (front + 1) % capacity

A simple implementation:

C++ 
class CircularQueue {
    vector<int> q;
    int front = 0;
    int rear = 0;
    int count = 0;

public:
    CircularQueue(int capacity) : q(capacity) {}

    bool push(int x) {
        if (count == q.size())
            return false;

        q[rear] = x;
        rear = (rear + 1) % q.size();
        count++;

        return true;
    }

    bool pop() {
        if (count == 0)
            return false;

        front = (front + 1) % q.size();
        count--;

        return true;
    }
};

Complexity: O(1) enqueue/dequeue.

17. Implement a hash table

For interview purposes, the basic idea is array + hash function + collision handling.

Using separate chaining:

C++ 
class HashTable {
    static const int SIZE = 10;

    vector<pair<int, string>> table[SIZE];

    int hashFunction(int key) {
        return key % SIZE;
    }

public:
    void insert(int key, string value) {
        int index = hashFunction(key);

        for (auto& p : table[index]) {
            if (p.first == key) {
                p.second = value;
                return;
            }
        }

        table[index].push_back({key, value});
    }

    string* find(int key) {
        int index = hashFunction(key);

        for (auto& p : table[index]) {
            if (p.first == key)
                return &p.second;
        }

        return nullptr;
    }
};

Collision is handled using separate chaining.

21. Implement an LRU cache

Interview answer: Use:

  • list for maintaining recency order
  • unordered_map for O(1) lookup

unordered_map

key → list iterator

list

MRU → ... → LRU

Implementation:

C++ 
class LRUCache {
    int capacity;

    list<pair<int, int>> items;

    unordered_map<int, list<pair<int, int>>::iterator> mp;

public:
    LRUCache(int capacity)
        : capacity(capacity) {}

    int get(int key) {
        if (!mp.count(key))
            return -1;

        auto it = mp[key];

        int value = it->second;

        items.splice(items.begin(), items, it);

        return value;
    }

    void put(int key, int value) {
        if (mp.count(key)) {
            auto it = mp[key];

            it->second = value;

            items.splice(items.begin(), items, it);
            return;
        }

        if (items.size() == capacity) {
            auto last = items.back();

            mp.erase(last.first);
            items.pop_back();
        }

        items.push_front({key, value});
        mp[key] = items.begin();
    }
};

Complexity:

  • get: average O(1)
  • put: average O(1)

Very common interview question: Why list?

Because once we have an iterator, moving/removing a list node is O(1).

24. Implement a min heap/max heap

Using a vector, a binary heap uses:

parent = (i - 1) / 2

left = 2 * i + 1

right = 2 * i + 2

For a max heap:

C++ 
class MaxHeap {
    vector<int> heap;

public:
    void push(int x) {
        heap.push_back(x);

        int i = heap.size() - 1;

        while (i > 0) {
            int parent = (i - 1) / 2;

            if (heap[parent] >= heap[i])
                break;

            swap(heap[parent], heap[i]);
            i = parent;
        }
    }

    int top() const {
        return heap.front();
    }

    void pop() {
        if (heap.empty())
            return;

        heap[0] = heap.back();
        heap.pop_back();

        int i = 0;

        while (true) {
            int left = 2 * i + 1;
            int right = 2 * i + 2;
            int largest = i;

            if (left < heap.size() &&
                heap[left] > heap[largest])
                largest = left;

            if (right < heap.size() &&
                heap[right] > heap[largest])
                largest = right;

            if (largest == i)
                break;

            swap(heap[i], heap[largest]);
            i = largest;
        }
    }
};

Complexity:

  • top: O(1)
  • push: O(log n)
  • pop: O(log n)

One of the most important STL traps:

C++

old memory
[1][2][3]
   ↓ reallocation
new memory
